Lesson 1’s run has a fatal flaw: give it while (1); and it waits forever. CodeArena’s worker would freeze on the first infinite loop anyone submits. Today you give run a deadline, and find out why stopping a program is harder than it looks: it can ignore you, sleep instead of spinning, or leave its children behind.

Why this matters

Time Limit Exceeded is the verdict a judge hands out most, and the one that’s hardest to get right. It’s also behind I-17, the bug you met on Monday: killing docker run doesn’t stop the container. By the end of this lesson you’ll be able to explain exactly why, because it’s the same mistake you’re about to make, and fix, in C.

1. Two clocks

“How long did it run?” has two answers, and a judge needs both.

  • Wall-clock time is what a clock on the wall would show between start and end. It keeps ticking whatever the program does: computing, sleeping, or waiting for input that never comes.
  • CPU time counts only the moments the program actually runs on a core. A sleeping program gets almost none.

Try it (2 minutes):

time sleep 1
time python3 -c "sum(range(30_000_000))"

real is wall-clock time. user and sys are CPU time, spent in your code and in the kernel on your behalf. sleep 1 takes a full second of real and almost zero CPU. The Python sum is the opposite: real ≈ user, because it computes the whole time.

The IOI’s sandbox has both: --time limits CPU time and --wall-time limits wall-clock time, as two separate options (isolate’s manual).

So a CPU limit alone can’t stop sleep(60), or a program blocked reading input you never send. The deadline that stops hangs is a wall-clock deadline. CPU time is still what you report and compare, and lesson 6 enforces it with cgroups. Today: the wall clock.

2. Signals: a tap on the shoulder, or the floor disappearing

To stop a process, you send it a signal: a small number that the kernel delivers on your behalf. The kernel marks it pending, and the next time the process passes through the kernel, the signal’s disposition runs. That’s one of three things:

  • the default action, which for most signals means terminating the process (sometimes with a core dump);
  • a handler, a function the program installed to run instead;
  • nothing, if the program asked to ignore that signal.

So most signals are a tap on the shoulder: the program decides what happens. Two are different. SIGKILL and SIGSTOP can never be caught, blocked or ignored. With SIGKILL, the program doesn’t get a say: the kernel just tears it down.

Try it (3 minutes). A Python process that ignores SIGTERM:

python3 -c 'import signal, time; signal.signal(signal.SIGTERM, signal.SIG_IGN); time.sleep(300)' &
kill -TERM $!; sleep 0.5; ps -o pid,stat,args -p $!
kill -KILL $!; sleep 0.5; ps -o pid,stat,args -p $!

After -TERM, it’s still listed. After -KILL, it’s gone. ($! is the PID of the last background job. And despite its name, kill sends any signal: the name is historical.)

docker stop is polite: SIGTERM, then SIGKILL after a grace period of 10 seconds on Linux (Docker docs), so a database can flush its files. Right for services, wrong for a judge.

For a judge, the rule follows: at the deadline, SIGKILL, with no grace period. A submission has nothing worth cleaning up, and a grace period is just more time for a hostile program to use.

3. Waiting, with a deadline

In lesson 1, waitpid(pid, &status, 0) slept until the child ended. With a deadline, that’s the problem: if the child never ends, neither does waitpid. There are three classic ways out.

  1. Poll. waitpid(pid, &status, WNOHANG) never sleeps: it returns the PID if the child has ended, and 0 if it’s still running. Ask, check the clock, nap for a millisecond, ask again. Simple, and easy to get right. Use this today.
  2. An alarm. alarm() asks the kernel to send you SIGALRM later. If you install a handler with sigaction (without SA_RESTART), the blocked waitpid returns -1 with errno == EINTR when the alarm fires. It’s the classic Unix way, and it’s fiddly.
  3. A pidfd. Since Linux 5.3, pidfd_open(pid) gives you a file descriptor for a process, which becomes readable when the process ends. poll() on it with a timeout gives you “wake me when it ends or when time’s up”, with no busy loop. It’s the modern answer, and today’s challenge.

Which clock? Measure with clock_gettime(CLOCK_MONOTONIC, …), never with the time of day. The time-of-day clock (CLOCK_REALTIME, what date prints) can be set: by NTP, by an administrator, or by WSL resyncing with Windows. It can jump forwards, or even backwards. The monotonic clock only moves forward.

This isn’t theory. While this lesson’s checker was being written, the wall clock on this very machine jumped back mid-run, and the checker measured a run that took −371 ms. The checker now uses a monotonic clock.

4. Killing everything it started

Your child isn’t always alone. sh -c 'sleep 100; echo done' is a shell, which forks sleep as its child. Kill the shell, and what happens to sleep?

Try it (2 minutes):

sh -c 'sleep 31.4; echo done' &
sleep 0.2; kill -KILL $!
sleep 0.2; ps -o pid,ppid,args -C sleep
pkill -f 'sleep 31.4'           # clean up

sleep 31.4 is still there, with a new parent. When a process dies, its children don’t die with it. They become orphans, adopted by init (PID 1) or by the nearest ancestor that registered as a subreaper, and they carry on. In a judge, every orphan is a process you forgot to stop, holding memory and CPU.

Process groups

Every process belongs to a process group, identified by a number, the PGID. A child starts in its parent’s group. A process can start a new group with itself as the leader by calling setpgid(0, 0), and the new group’s ID is then its own PID. Every process it starts afterwards inherits that group.

And kill understands groups: a negative number means “every process in this group”. kill(-4121, SIGKILL) kills the leader and everything it started. That’s how your shell’s Ctrl+C stops a whole pipeline at once.

The catch

Look at PID 4123. A process can leave its group: setsid() starts a new session and a new group, and setpgid can move a process too. A hostile submission can do that on purpose, and your kill(-pgid) misses it. Process groups were designed for shells and job control, not as a security wall. Your checker includes a program that escapes this way, and it will survive your kill. That’s expected: lesson 5 closes the hole with a PID namespace (kill its PID 1, and the kernel kills everything inside), and lesson 6 with cgroup.kill.

Before you build it, predict it. Each round draws new trees: groups or not, an escape or not, SIGTERM or SIGKILL. Getting these right in your head is what makes the lab quick.

5. I-17, explained

Now Monday’s bug makes sense. When you run docker run …, the process you started is only a client. It sends a request to the Docker daemon, and the daemon’s helpers (containerd, then a small containerd-shim) start the container’s process. That process is not a child of docker run: it lives in another branch of the process tree entirely.

  • SIGKILL the client, and you’ve killed the messenger. The client can’t pass SIGKILL on (nobody can catch it), so the container never hears about it and keeps running. That’s the orphan story, one level up.
  • SIGTERM the client, and it forwards the signal to the container’s first process (docker run’s --sig-proxy is on by default). But inside a container, that process is PID 1, and PID 1 only receives signals it has installed a handler for (pid_namespaces(7)), so nothing happens. You’ll build one in lesson 5 and see it yourself.

The fix follows the same rule as today: stop the work through whoever owns it. Give every container a unique name, and at the deadline ask the daemon to kill it by name (docker kill <name>). You’ll build exactly that in lesson 8.

6. Build: run, with a deadline

Usage: ./run -t <ms> <program> [args...]

Runs the program with a wall-clock deadline of ms milliseconds, then prints exactly two lines on stdout:

  • line 1: exit N, signal S, or timeout if the deadline stopped it;
  • line 2: time_ms=T, the wall-clock time from just before fork to the end.

At the deadline, the program and everything it started must be killed and reaped. Wrong usage (no -t, a value that isn’t a positive number, no program) prints a usage line on stderr and exits with 2.

Hint: the shape of the loop, in words

Repeat: ask waitpid with WNOHANG. If the child has ended, leave the loop and report as in lesson 1. If not, check the clock: past the deadline, send SIGKILL, then call a blocking waitpid to reap it (otherwise it stays a zombie), and report timeout. Otherwise, sleep 1 ms and ask again.

Why sleep 1 ms between checks?

Without it, your loop asks the kernel millions of times a second, using a whole CPU core just to wait. Your judge would compete for the CPU with the very program it’s timing, and slow it down. One millisecond of sleep makes the waiting almost free, at the cost of up to 1 ms of lateness.

3

Leave nothing behind

Make “Nothing left behind” green: when a shell started sleep, both must be dead after your timeout. Use a process group. Where must setpgid be called? (Lesson 1 told you where every sandbox gets built.)

Hint: a race hides here

After fork, you don’t know whether the parent or the child runs first. If the parent reaches the deadline and calls kill(-pid, …) before the child has called setpgid(0, 0), the group doesn’t exist yet. The fix that shells use is to call it in both places: setpgid(0, 0) in the child before exec, and setpgid(pid, pid) in the parent right after fork. The parent’s call can fail if the child has already called exec. That’s fine: it means the child got there first.

Replace the polling loop with a pidfd: pidfd_open(pid, 0) (from <sys/pidfd.h>, glibc 2.36 or later), then poll() on it with the time left as the timeout. It wakes exactly when the child ends or the deadline passes, and never in between. To see the difference, compare the CPU your runner itself uses while waiting on a sleeper:

With polling, user + sys comes to tens of milliseconds (about 30 ms when this lesson was tested): three thousand wake-ups to ask “done yet?”. With a pidfd it drops to almost nothing. Read pidfd_open(2) first.

7. What this means for a judge

  • Two limits. A wall-clock deadline stops hangs, and CPU time is the fair measure of speed. Your runner has the first; cgroups will give it the second (lesson 6).
  • SIGKILL, no grace. Politeness is for services, not for strangers’ code.
  • Kill the work, not the messenger. Whatever you kill must be what’s actually running, or the owner of it: the group, the PID namespace, the container through its daemon.
  • Groups are not walls. They stop accidents, not attacks. The escape you just watched is why real judges use namespaces and cgroups.

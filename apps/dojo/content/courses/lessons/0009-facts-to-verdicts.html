Your runner reports facts: how a program ended, what it printed, how long it took. A judge turns those facts into one word a user cares about: Accepted, or what went wrong. Today you write that logic, test-first, against a fake runner you script line by line. It’s the part of CodeArena an interviewer can read in one sitting, so it has to be exactly right.

Why this matters

Two distinctions decide whether users trust your judge. First, whitespace must never decide a verdict: a missing final newline is the most common Wrong Answer that should have been Accepted. Second, a user’s failure is a verdict, and your failure is an error: if Docker is down, the submission didn’t fail, your judge did.

1. Six verdicts, one order

Every test ends one of six ways, and the order you check them in matters, because a program can hit several at once (crash and print the right answer, flood and time out):

  1. TLE, Time Limit Exceeded: your deadline stopped it (lesson 2).
  2. MLE, Memory Limit Exceeded: the OOM killer, inside its cgroup (lessons 6 and 8).
  3. OLE, Output Limit Exceeded: it printed past the cap (lesson 3).
  4. RE, Runtime Error: killed by a signal, or a non-zero exit code (lesson 1). Its output isn’t even read.
  5. WA, Wrong Answer: it ended normally, but the output doesn’t match.
  6. Otherwise this test passed; when every test passes, AC, Accepted.

Limits first, then how it ended, and only then what it printed. A program that prints the right answer and then segfaults gets RE, not AC: the judge never got as far as reading.

2. Compare tokens, not bytes

Expected 5\n, the program printed 5: byte-for-byte that’s different, and the answer is still right. So judges compare tokens: split both outputs on any whitespace (spaces, tabs, newlines, \r), and compare the two sequences. That’s what Codeforces’ standard checker, wcmp in testlib, does, and what your ADR-006 says. Tokens themselves are compared exactly: 1.0 isn’t 1, and YES isn’t yes.

Problems with floating-point answers need a checker with a tolerance, and problems that accept any valid answer need a custom checker that verifies it. Both are the challenge, not the core.

3. The loop, and what isn’t a verdict

The judge runs a problem’s tests in order, and stops at the first failure: the verdict and the failing test’s number are known, and every further run would cost a container start for nothing. It reports the slowest time among the tests that ran. Two things must never become verdicts:

  • An infrastructure failure. If the runner can’t reach Docker, it throws, and the judge lets the error through. The queue will retry the job (lesson 14). Turning it into RE would blame the user for your outage.
  • An empty test list. A problem with no tests can’t accept anything. It’s a bug in your data, so it’s an error too.

Test it with a fake

The judge depends on a runner, but its tests must not start containers: they’d be slow and need Docker. So the judge takes the runner as a parameter (in CodeArena, the CODE_RUNNER port), and the tests pass a fake that returns scripted facts and counts its calls. “A wrong answer on test 2” becomes: script test 1 to pass and test 2 to print nope, then assert the verdict, the test number, and that the runner was called exactly twice. That’s the port-and-adapter shape your worker already has, paying off.

5. What this means for a judge

  • The checker is domain logic. Pure, no input/output, tested with a table of cases: it belongs in the worker’s domain folder.
  • The loop is application logic. It depends on the CODE_RUNNER port, never on Docker, so the fake from your worker’s first day becomes its test double.
  • Verdicts are for users, errors are for you. The queue’s retries and dead-letter state (lesson 14) only work if the judge never hides an error inside a verdict.

1. How to read a plan

A plan is a tree. Each node pulls rows from the nodes below it, so you read it from the innermost, most indented lines outward; the top line produces the final result. This is the slow version of today’s third query, simplified:

Limit  (cost=0.71..64.95 rows=20)
       (actual time=2.83..5.12 rows=20 loops=1)
  Buffers: shared hit=6355 read=13
  ->  GroupAggregate  (actual rows=20 loops=1)
        ->  Nested Loop Left Join  (actual rows=6575 loops=1)
              ->  Index Scan using problems_pkey on problems p
                    (actual rows=21 loops=1)
              ->  Index Scan using submissions_problem_status on submissions s
                    (actual rows=313 loops=21)
                    Buffers: shared hit=6352 read=13
  • cost=… is the planner’s estimate, in arbitrary units: startup cost, then total. actual time is measured, in milliseconds (using EXPLAIN).
  • rows and time are per loop. The inner scan ran 21 times, once per problem, at 313 rows each: about 6,573 rows in all. Multiply by loops, always.
  • Buffers counts pages: hit from Postgres’s memory, read from the operating system. Here, 6,352 of the 6,368 pages belong to one node. That’s where to look.

Keyset pagination

OFFSET 980 can’t jump: it produces 980 rows and discards them, so page 50 costs fifty times page 1. Keyset pagination (also called the seek method) asks for “the 20 rows after the last one I saw”: WHERE user_id = $1 AND (created_at, id) < ($ts, $id) ORDER BY created_at DESC, id DESC LIMIT 20. With an index on (user_id, created_at DESC, id DESC), it lands on the cursor and reads 20 entries, whatever the page (Use The Index, Luke: fetch next page). The id breaks ties between equal timestamps, so no row is skipped or shown twice.

The cursor must carry the values, not just an id. A cursor that’s only an id forces the query to look that row up, and once it’s deleted, there’s nothing to look up: the next page comes back empty. That’s I-10, exactly.

N+1 and counting

An ORM loop that fetches each row’s relation separately sends N+1 queries; each pays a round trip, parsing and planning. Prisma documents the problem and its fixes (query optimization). For counts, remember that count(*) counts rows while count(column) counts non-null values (aggregate functions): over a LEFT JOIN, that difference is a wrong answer.

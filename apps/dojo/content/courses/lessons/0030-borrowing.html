Moving everything around would make Rust unusable: you’d hand a string to a function and never see it again. So you lend it. A borrow is a pointer the compiler tracks, and one rule makes it safe: many readers or one writer, never both. Today you learn the rule and why it exists, then rebuild lesson 9’s output comparator so that every token it looks at is a slice of the program’s output. No copies at all.

Why this matters

A judge compares megabytes of output per submission. In C you’d return pointers into the output buffer and hope nobody frees it first. In Rust you do the same thing, and the compiler proves nobody can. That combination, C’s speed with checked safety, is the whole case for Rust in infrastructure.

1. References

&s creates a shared reference to s: you can read through it, and s keeps ownership. &mut s creates a mutable reference: you can change s through it. Both are plain pointers at runtime, with no reference counting and no cost. All the checking happens at compile time (The Book, §4.2).

fn count_words(line: &str) -> usize {      // borrows: reads, gives back
    line.split_whitespace().count()
}
fn add_newline(buf: &mut String) {         // borrows exclusively: changes it
    buf.push('\n');
}

2. The rule: many readers or one writer

At any moment, a value can have any number of shared references, or exactly one mutable reference, never both. And a reference can never outlive the value it points to. A borrow lasts from where it’s created to its last use, not to the end of the block, so most code that’s safe compiles without ceremony.

Why so strict? Look at the code The Book uses (§8.1):

let mut v = vec![1, 2, 3];
let first = &v[0];       // a pointer into v's buffer
v.push(4);               // full? push allocates a new buffer and frees the old one
println!("{first}");     // first would point at freed memory

The same code in C++ compiles and reads freed memory, sometimes, depending on the capacity. Rust refuses it with E0502: first is a reader still in use, and push wants to write.

3. Slices: borrowing part of something

A slice is a pointer and a length into memory someone else owns: &str for text, &[T] for elements. "hello" is a &str pointing into the program’s binary; &line[2..5] points into line; split_whitespace() yields slices of its input, one per token, without allocating.

So the right parameter type for a function that reads text is &str: it accepts a &String, a literal, or a slice of a bigger output. For a list, &[T]. Take &mut only to change, and take ownership only to keep.

The comparator

split_whitespace() is an iterator of &str. Iterators compare with .eq(), step with .next() (which returns an Option), and skip with .nth(). For first_difference, walk both iterators together; a match on the pair (e.next(), a.next()) reads well. For trim_lines, iter_mut() lends each line mutably, trim_end() tells you how much to keep, and truncate keeps the buffer.

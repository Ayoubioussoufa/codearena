1. Paths and folders

Path is to PathBuf what &str is to String: a borrowed view and its owned version. Paths aren’t Strings, because file names on Linux are bytes, not necessarily UTF-8 (std::path).

for entry in fs::read_dir(dir)? {          // io::Result<DirEntry>, in no set order
    let path = entry?.path();               // tests/data/sum/10.in
    path.extension();                       // Some("in")
    path.file_stem();                       // Some("10")
    dir.join("10.out");                     // tests/data/sum/10.out
}

read_dir’s order depends on the filesystem, so sort, and sort the right thing: as strings, "10.in" comes before "2.in". Parse the stem to a number first.

2. Reading and writing, with buffers

  • fs::read_to_string(path)? for small files you need whole (an answer file).
  • BufReader::new(file).lines() for big files, lazily. Unbuffered reads ask the kernel for every few bytes.
  • stdout is line-buffered, even into a pipe, and println! locks it on each call (println! docs). Measured on Rust 1.99: 1,000 println!s into a pipe made 1,000 write system calls; the same lines through let mut out = BufWriter::new(io::stdout().lock()); and writeln!(out, …)? made 2.
  • A BufWriter flushes when dropped. std::process::exit runs no destructors (its docs say so), so flush before exiting, or return from the function and exit afterwards, as the starter’s main does.

3. Pipes, a cap, and lesson 3’s deadlock

let mut child = Command::new(prog)
    .stdin(Stdio::from(File::open(input)?))    // the file IS its stdin
    .stdout(Stdio::piped())                    // a pipe you read
    .stderr(Stdio::null())
    .spawn()?;
let mut out = Vec::new();
child.stdout.take().unwrap()                   // the pipe: move it out of the Child
    .take(OUTPUT_CAP + 1)                      // Read::take: stop after N bytes
    .read_to_end(&mut out)?;

A Linux pipe holds 64 KiB by default (pipe(7)). If you stop reading while the pipe is still open and then wait(), a program that keeps writing blocks on the full pipe, and you block in wait: forever. In the code above the pipe happens to be dropped right after read_to_end, so the flooder dies of SIGPIPE on its next write, which is lucky rather than designed. A program that stops writing but keeps running would still hang you. So over the cap, child.kill() before child.wait(), every time.

4. Build minijudge

minijudge <tests-dir> <program> [args…] prints test N: AC (or WA, OLE, RE (exit N), RE (signal S)) per test in numeric order, then passed X/Y. Exit code 0 if all passed, 1 if any failed, 2 if the judge itself couldn’t run, with a minijudge: … line on stderr. The kit has five C programs in progs/ (a right one, a wrong one, a crasher, an exit 3, a flood) and a tests folder. The tests drive your binary with a 10-second watchdog, so a hang fails instead of freezing.

Docker doesn’t replace them. It adds walls around them, and lessons 4 to 7 build those walls. Today you build the core, with no walls. 1. A process, and the kernel that owns it

A program is a file on disk. A process is a program while it runs: its own memory, the CPU’s registers, its open files, a number called its PID, and a parent, the process that started it.

Try it (2 minutes), in your terminal:

grep -E '^(Name|Pid|PPid)' /proc/self/status
echo $$

/proc/self is the kernel describing whichever process reads it, here grep. $$ is your shell’s PID. Compare it with PPid, then run the first line again: Pid changes and PPid doesn’t. Every command you type is a brand-new process, and your shell is its parent.

OSTEP calls this design limited direct execution. Your code runs directly on the CPU, at full speed, but within limits, and the limits are enforced every time it asks the kernel for something. (OSTEP, chapter 6)

Now comes the most important idea of the whole track. Your process can’t touch the disk, the network, or another process on its own. The CPU runs it in user mode, where the instructions that drive hardware are forbidden. To do anything outside its own memory, a process asks the kernel through a system call: open, write, connect, fork, kill… The CPU switches into kernel mode. The kernel checks the request, then carries it out or refuses it, and switches back.

A hostile program can only hurt you through system calls. So a sandbox is a set of rules about which system calls the kernel will allow, and what it lets them see.

Namespaces, cgroups, capabilities and seccomp, the four words from Monday, are four kinds of rules. You’ll build each one by hand in lessons 4 to 6.

2. How one process starts another

Three system calls, and you’ve written all three before.

  • fork() asks the kernel to copy the calling process. Afterwards, two processes run the same code from the same line, each with its own copy of the memory. The only difference is what fork returns: 0 in the child, the child’s PID in the parent, or -1 if it failed.
  • execvp(file, argv) replaces the program inside the calling process. The PID stays the same, but the code and memory are new. If it works, it never returns, because the code that called it no longer exists. It returns -1 only when it fails, for example when the file doesn’t exist.
  • waitpid(pid, &status, 0) puts the parent to sleep until that child ends. Then the kernel fills in status, one int that says how the child ended.

Why two calls, and not one “run this program”?

Because exec replaces whoever calls it. If your shell called exec itself, the shell would become ls, and when ls finished, your shell would be gone. So the shell forks a copy of itself and lets the copy become ls.

A child that has ended but hasn’t been waited for stays in the process table as a zombie, holding its status until the parent collects it. That’s why every fork needs a wait.

And the gap between fork and exec turns out to be the most useful moment in Unix. The child is already a separate process, but it’s still running your code, so it can change its own settings before the new program starts. In minishell, that’s where you called dup2 to wire pipes and redirections. In lesson 2, it’s where you’ll set limits. It’s also where a container runtime builds the container. The gap between fork and exec is where every sandbox is built.

3. Build run

Usage: ./run <program> [args...]

Runs the program, waits for it, then prints exactly one line on stdout:

  • exit N if the program ended by itself with exit code N;
  • signal S if signal number S killed it.

If the program can’t be started, the child prints the reason on stderr and exits with 127. With no program at all, run prints a usage line on stderr and exits with 2.

Fork, exec, wait, and look at the raw status

Write the smallest version you can. Fork. In the child, exec the program named on the command line. In the parent, wait for the child, then print the raw status in hex:

printf("raw status = 0x%04x\n", status);

Skip error handling for now. Build with bash check.sh build, then fill this table from your own runs:

Now read the hex like a detective. Where does the exit code live? Where does the signal number live? Why didn’t exit(300) give 300?

Hint: how do I build the child’s argv?

Look at your own argv. For ./build/run sh -c 'exit 5', it holds "./build/run", "sh", "-c", "exit 5", then NULL. The child needs exactly that list without its first element, still ending with NULL. You don’t need to copy anything.

Answer: what the bits mean (open after filling the table)

You should have seen 0x0000, 0x0300, 0x2c00, 0x000b, 0x0006 and 0x0009. The kernel packs two different stories into one int:

bits 15–8the exit code, if it ended by itself
bit 7core?
bits 6–0the signal that killed it (0: none)

exit(3) puts 3 in the high byte (0x03 << 8 = 0x0300), and the low byte stays 0, meaning “no signal”. SIGSEGV is signal 11: the high byte stays empty and the low byte holds 0x0b. And exit(300)? There are only 8 bits for the code. 300 is 0x12c, so the parent receives 0x2c, which is 44. That’s why exit codes run from 0 to 255.

This layout is how Linux happens to do it. POSIX, the standard, only promises the macros in step 2, so real code always uses the macros and never shifts bits by hand. You looked at the bits to understand the macros, not to replace them.

2

Decode it with the macros

Replace the raw print with the real output: exit N or signal S. The kernel gives you four macros to read a status (waitpid(2)):

  • WIFEXITED(status): true if the child ended by itself, by returning from main or calling exit;
  • WEXITSTATUS(status): its exit code. Read it only when WIFEXITED is true;
  • WIFSIGNALED(status): true if a signal killed it;
  • WTERMSIG(status): that signal’s number. Read it only when WIFSIGNALED is true.

Run bash check.sh. The first two groups should now be green.

3

When exec fails

Run ./build/run ./build/no-such-program. When execvp fails, it returns -1, and the child keeps running… your code. Decide what the child should do at that point, then make the case pass: print the reason with perror, then end the child with _exit(127).

Why 127, and why _exit and not exit?

127 is the shell’s code for “command not found”, and 126 means “found, but not executable”. bash uses the same codes, so a caller can tell “your program failed” apart from “your program never started”.

_exit, because the child is a copy of the parent, including whatever printf had buffered but not yet written. exit() would flush that copy, and the parent’s text would appear twice. _exit ends the process without touching those buffers.

Usage, then all green

With no program, run must print a usage line on stderr and exit with 2, the usual code for “you called me wrong”. Then run bash check.sh until you see 14 green ticks.

★

Challenge: rebuild the shell’s 137

Optional, to stretch your brain. Make run itself exit the way a shell reports a child: N for exit N, and 128 + S for signal S. Then:

./build/run ./build/selfkill; echo $?
./build/run sh -c 'exit 137'; echo $?

Both print 137. You’ve just rebuilt the convention behind Docker’s 137, and found its flaw: squeezed into one number, “killed by SIGKILL” and “exited with 137” look the same. Your run prints different lines for them, but $? can’t tell them apart. The checker shows this challenge as a bonus at the end.

4. What this means for a judge

Look at the checker’s output again, this time as a judge would.

  • The kernel is the witness. The child can’t fake how it ended, because the kernel writes status, not the program. That’s why a judge trusts waitpid over anything the program prints.
  • “Runtime error” isn’t one thing. The C programs that crashed were killed by a signal: the CPU faulted, and the kernel sent SIGSEGV or SIGFPE. But python3 -c '1/0' ended with exit 1. Python checks the divisor itself, prints a traceback on stderr, and exits normally with 1, and Node behaves the same way. So for a judge, Runtime Error means killed by a signal or a non-zero exit code.
  • One number loses information. exit 137 and signal 9 are different facts, and only the full status keeps them apart. Docker’s command line gives you the shell’s single number. That’s why Monday’s experiment needed docker inspect and its OOMKilled field.

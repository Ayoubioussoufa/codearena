You’ve built a sandbox. Now you try to break it, on purpose, with the six attacks a stranger will try on day one. Then a harder question: if one of your walls quietly went missing next month, would your tests notice? Today you find out, with a technique most junior engineers have never heard of.

Why this matters

The adversarial suite is the single most convincing file in CodeArena. “Here are six attacks on my judge, each contained, each test proving which wall held, and each one fails if that wall is removed” is a sentence an interviewer remembers. The last part is the one almost nobody can say.

1. Test the wall, not the verdict

A naive sandbox test checks the verdict: “the fork bomb gets a verdict and doesn’t crash the judge”. But a fork bomb’s parent ends normally whether it created 60 processes or 500, so that test passes with or without --pids-limit. It tests nothing about containment.

A containment test makes the attack report what it could do, and asserts on that:

Why /etc/passwd? Reading it is harmless: every image has one. The question is whose. Alpine’s root line ends in /bin/sh; your Ubuntu host’s ends in /bin/bash. Seeing the host’s would mean your mount namespace leaked.

And after every attack, check the host too: no container left, Docker still answering. A wall that holds but leaves debris isn’t containment.

2. Would your tests notice? Mutation testing

Code coverage tells you a line ran during the tests; it doesn’t tell you a test would fail if that line were wrong. Mutation testing answers that question directly: change the code on purpose (each changed version is a mutant), run the suite, and count the mutants that no test catches. A surviving mutant is a protection your tests can’t see.

For a sandbox, the mutants are obvious: remove one protection at a time. This lab’s checker ships six weakened runners (no network isolation, writable root, no memory limit, no pids limit, capabilities kept, running as root), and runs your suite against each. Every one must make at least one of your attacks fail. Writing to /etc as nobody, for example, fails even on a writable root, so an attack built on it lets the read-only mutant survive. The lab will show you that, unless you’ve thought of it.

Tools do this for regular code: Stryker mutates JavaScript and TypeScript (flips a <, removes a call) and reports surviving mutants. Today you do it by hand, on infrastructure, which is rarer.

The obvious four

Fork bomb, infinite loop, memory, network, each printing what it could do, each expect asserting on that. Run bash check.sh: they should be contained by your runner, and catch four of the six mutants.

Hint: a fork bomb that reports

Loop up to 500 times: os.fork(); in the child, sleep a few seconds then os._exit(0); in the parent, count. Catch OSError (the pids limit says no) and stop. Print the count. When the parent exits, PID 1 of the container is gone, and the kernel kills the sleeping children (lesson 5).

The two subtle ones

Write the filesystem attack and the identity attack so they catch the read-only, capabilities and root mutants. All 14 cases should pass.

Hint: proving read-only

Two observations that change with the flag: the root’s mount options (find the line in /proc/mounts whose mount point is /; its options start with ro or rw), and whether a script you write into /tmp and chmod can run (with noexec, running it raises PermissionError).

4. What this means for a judge

  • Every protection gets a test that would notice it missing. That’s the standard: a protection without such a test will quietly disappear in a refactor.
  • Check the host, not just the verdict. No leftovers, the daemon still answering, nothing written outside the run’s folder.
  • Name the mechanism. Comment each attack with the wall that stops it (--pids-limit, not “the sandbox”): the file becomes documentation an interviewer can read.

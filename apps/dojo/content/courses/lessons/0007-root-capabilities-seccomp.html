Namespaces hide the world, cgroups ration it. But inside your box the program is still root, and root can do things no namespace hides: mount filesystems, load kernel modules, trace other processes. Today you take those powers away permanently, then go one level lower and forbid system calls outright, with a filter you write by hand in the kernel’s own bytecode.

Why this matters

Every container escape starts with something the program was still allowed to ask the kernel for. Capabilities and seccomp are the two layers that shrink what it can ask. They’re also the two words in “almost no junior candidate can talk about seccomp”, and after today you’ll have written one.

1. Root is a bundle of powers

Since Linux 2.2, “root” isn’t one switch. Its powers are split into about forty capabilities, each one checked separately (capabilities(7)): CAP_SYS_ADMIN to mount filesystems and create most namespaces, CAP_CHOWN to change owners, CAP_NET_RAW to send raw packets, CAP_SYS_PTRACE to trace processes, and so on. A process carries several sets of them:

  • effective: what the kernel checks right now;
  • permitted: what it may switch on;
  • bounding: the ceiling, which nothing can ever exceed again once it’s lowered.

Try it (2 minutes). The same “root”, with and without its powers:

unshare --user --map-root-user grep -E 'CapEff|CapBnd' /proc/self/status
unshare --user --map-root-user unshare --mount true; echo "exit=$?"

CapEff is a bitmask: 000001ffffffffff means every capability is on (inside the user namespace). And with them, root can build itself a new mount namespace. Your guard will turn every one of those bits off.

The trap: exec refills root

Here’s the subtle part, and the lab tests it. You might clear the effective and permitted sets with capset, then exec the program, and find its CapEff full again. When a process running as uid 0 calls execve, the kernel recomputes its capabilities, and for root that means “everything the bounding set allows” (capabilities(7), “Transformation of capabilities during execve()”). So you must lower the ceiling itself: prctl(PR_CAPBSET_DROP, cap) for every capability. That’s what docker run --cap-drop ALL does.

This lesson was tested with exactly that mistake: without the bounding-set drop, CapEff after exec read 000001ffffffffff, every power back.

2. no_new_privs: no way up

Even a powerless process can still exec a setuid program, one that runs as its file’s owner. That’s how sudo and passwd work, and it’s a way back up. One flag closes it: prctl(PR_SET_NO_NEW_PRIVS, 1) promises that execve will never grant privileges again, setuid bits and file capabilities included (prctl(2)). It’s inherited, and it can never be unset. Docker’s flag for it is --security-opt no-new-privileges.

It also unlocks the next layer: an unprivileged process may install a seccomp filter only after setting it (seccomp(2)).

3. seccomp: a filter on every system call

Lesson 1 said a hostile program can only hurt you through system calls. seccomp takes that literally. You hand the kernel a small program, written in BPF (the kernel’s tiny bytecode), and the kernel runs it on every system call the process makes, before anything else happens. The program reads the call’s number and architecture, and returns an action:

ReturnWhat the program sees
SECCOMP_RET_ALLOWthe call runs normally
SECCOMP_RET_ERRNO | EPERMthe call fails with that error, as if the kernel had refused it. The program can react
SECCOMP_RET_KILL_PROCESSinstant death by SIGSYS, signal 31. It never sees the call return

Your filter is a denylist: check the architecture (a 32-bit call has different numbers, which is a classic bypass), then refuse socket with EPERM, kill on unshare and ptrace, and allow the rest. Each line is a macro that builds one BPF instruction:

// load the architecture
BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, arch)),
// x86-64? skip the next line
BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, AUDIT_ARCH_X86_64, 1, 0),
// anything else: die
BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),
// load the call's number
BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, nr)),
/* …one BPF_JUMP per call you refuse, each followed by its BPF_RET… */
// everything else
BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),

A BPF_JUMP has two offsets: how many instructions to skip if the test is true, and if it’s false. (…, __NR_socket, 0, 1) reads “if it’s socket, go to the next line (the refusal); otherwise skip it”. That’s the whole language you need.

Docker’s default profile is the opposite, an allowlist: refuse everything, then allow the calls it names. In effect it “disables around 44 system calls out of 300+” (Docker docs). An allowlist fails safe when a new kernel adds a system call. That’s today’s challenge.

Before you build it, predict it. This drill mixes every wall from lessons 2 to 7, on purpose: telling them apart under pressure is what makes them stick.

4. Build guard

Usage: ./guard [-k] [-n] [-s] <program> [args...]

Forks a child that becomes root in a new user namespace (0 <your uid> 1, as in lesson 5), then, unless -k (keep) is given, drops every capability, bounding set included. -n sets no_new_privs. -s sets it too, then installs your filter: socket → EPERM, unshare and ptrace → kill, wrong architecture → kill, everything else allowed. Then it execs the program, and the parent prints exit N or signal S. No program: usage, exit 2.

The filter

Write the BPF program as an array of struct sock_filter, then install it after no_new_privs, as the last thing before exec. Make “The system-call filter” green: a Python socket fails with PermissionError, unshare dies with signal 31, and a plain shell still works.

Why install the filter last?

From the moment it’s installed, it applies to you too, and to everything you do afterwards, including the setup. Install it earlier, and your own unshare or prctl calls get filtered. The filter is inherited across fork and kept across execve, so installing it just before exec covers the program and everything it starts.

5. What this means for a judge

  • Your sandbox is complete, and you built every layer: namespaces (what it sees), cgroups (what it uses), capabilities and no_new_privs (what root can do), seccomp (which calls it may make), and the deadline (how long).
  • Docker gives you all of it, if you ask: --cap-drop ALL, --security-opt no-new-privileges, and its default seccomp profile, which applies unless you pass seccomp=unconfined. Lesson 8 maps every flag to the layer you wrote.
  • Defence in depth. Mounting is blocked twice: no CAP_SYS_ADMIN, and Docker’s filter refuses mount too. A sandbox is a stack of walls, each assuming the one before it might fail.

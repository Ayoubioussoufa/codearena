Postgres doesn’t “look up” a row. It reads pages from disk, 8 kB at a time, and the only question that matters for speed is how many. Today you watch a query read 2,750 pages to return 20 rows, then build the index that gets it down to 23, and learn exactly why column order decides whether an index helps at all.

Why this matters

This afternoon you seed a million submissions and write six before/after query plans. That’s also the evidence behind I-16, the index your schema has that can’t serve its own query. After today, you’ll see it without running anything.

1. Pages and the heap

A Postgres table is a file of fixed-size pages (8 kB by default), each holding as many rows as fit (page layout). The rows sit in no useful order: new ones go wherever there’s room. That unordered file is called the heap.

So without help, “find user 4242’s submissions” has one strategy: read every page and test every row. That’s a sequential scan. On the lab’s 300,000 submissions it reads about 2,750 pages, whether 10 rows match or 100,000. The unit of cost is the page, and EXPLAIN (ANALYZE, BUFFERS) counts them for you: that’s the “buffers” number your checker prints.

2. A B-tree: a sorted copy with a table of contents

An index is a second copy of some columns, kept sorted, where each entry points at its row in the heap. Postgres’s default kind is a B-tree: the sorted entries live in leaf pages, and a few levels of branch pages above them act as a table of contents.

                 [ root: … 3000 | 6000 … ]
                /            |             \
   [ branch … ]       [ branch: 4000 | 4200 | 4400 ]       [ branch … ]
                                    |
        leaf: (4242 → page 812) (4242 → page 1907) (4243 → page 33) …

Finding user 4242 means reading the root, one branch, and the leaf: three pages, not 2,750. Because each page holds hundreds of entries, the tree stays shallow: Markus Winand notes that real indexes with millions of entries have a depth of four or five (Use The Index, Luke: the tree). Then each matching row costs one more page from the heap, which is why a query matching 10 rows is cheap and one matching 100,000 isn’t.

If every column a query needs is in the index, Postgres can skip the heap entirely: an index-only scan. It still needs to know the rows are visible, which it learns from the visibility map that VACUUM keeps (index-only scans). That’s why the checker vacuums before measuring.

3. Column order is everything

A two-column index is sorted like a phone book: by the first column, then by the second within each value of the first. That one fact gives you every rule:

  • The leftmost prefix. (user_id, family) can find a user, or a user and a family. It can’t find a family alone: those entries are scattered across every user, so there’s nowhere to start (multicolumn indexes). That’s I-16.
  • Equality first, then the sort or the range. (user_id, created_at DESC): the equality lands on one contiguous slice, and inside it the rows are already in date order. ORDER BY created_at DESC LIMIT 20 reads 20 entries and stops: no sort at all (indexes and ORDER BY).
  • Backwards is free. A B-tree can be walked in either direction, so the same index serves ASC too.

4. The planner decides, from statistics

Having an index doesn’t mean Postgres uses it. The planner estimates what each strategy would cost, from statistics that ANALYZE collects, and picks the cheapest (using EXPLAIN). The key estimate is selectivity, the fraction of rows that match:

  • A few rows: an Index Scan, one heap page per row.
  • Hundreds to thousands, scattered: a Bitmap Heap Scan. It collects the matching page numbers from the index first, then reads each page once, in file order, instead of jumping back and forth (combining indexes). It can also combine two indexes with a BitmapAnd.
  • A large share of the table: a Seq Scan, because reading everything in order beats fetching most of it piece by piece.

That’s why, in the lab, your 8,000-submission user gets an ordered index walk, and the 10-submission user gets a bitmap scan plus a tiny sort. Both are right. A plan belongs to a query and its data, not to an index.

6. What this means for CodeArena

  • Every index answers a named query. Your schema already does this with comments (// profile history, cursor-paginated). Keep the habit: an index nobody can name a query for is pure write cost.
  • Seed before you measure. On 50 rows, everything is a Seq Scan and every plan is fast. That’s why today’s task starts with a million-row seed, skewed like real traffic.
  • Run ANALYZE after seeding. The planner works from statistics; stale statistics make plans that lie.

Queues and idempotency, on one page

From lessons 13 and 14.

The submission pipeline

POST /submissions → validate → INSERT row (PENDING)
                  → enqueue { id } (jobId = id) → 202 { id }
worker: take job → load row → claim → judge → write verdict → ack
GET /submissions/:id → the row (owner only; others get 404)

A reliable queue on Redis

StepCommandWhy
enqueueSADD q:ids id then LPUSH q:waiting jobrefuse duplicate ids; newest on the left
takeLMOVE q:waiting q:active RIGHT LEFTatomic: one worker per job, and it stays visible
ackLREM q:active 1 jobdone: nothing left to redeliver
failLREM, then back to waiting (attempts + 1) or to deadretry infrastructure errors only
recovermove active back to waitinga crash redelivers: at-least-once
  • 202, not 201: accepted, not finished. Row first, then the job. The id, never the code.
  • BullMQ does all of this, plus locks with renewal (a worker that stops renewing is "stalled" and its job redelivered), backoff, delays, priorities, events. jobId = submission id dedupes enqueues.
  • Exactly-once delivery doesn't exist across crashes: at-least-once delivery + idempotent processing.

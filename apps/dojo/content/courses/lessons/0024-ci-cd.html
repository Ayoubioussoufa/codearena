Until today, deploying CodeArena means SSH-ing in and typing commands, which works until the day you’re tired and type the wrong one. Today you build the pipeline that makes deploying boring: merge to main, tests run, images are built once and tagged with the commit, the server pulls them, checks they’re healthy, and rolls itself back if they aren’t. You test the rollback before you ever need it.

Why this matters

“Merge to main → images to the registry → deploy over SSH, and a rollback you’ve actually tried” is this afternoon’s task, word for word. And a deploy workflow holds your server’s SSH key and a token that can push images: it’s a security boundary, reviewed like one.

1. The shape of the pipeline

push to main
  └► test
      └► build: 3 images, each tagged with the commit SHA
          └► deploy, in the production environment
              └► ssh deploy@server ./deploy.sh <sha>
                  pull → up -d --wait → check /health
                  → record the tag, or roll back
  • Build once, deploy that. The image the tests passed against is the image that runs, tagged with the commit SHA. A tag that never changes means “what’s running?” has a one-word answer, and every past version is still in the registry.
  • Rollback is a deploy. A workflow_dispatch input tag lets you redeploy any earlier SHA from GitHub’s UI, with no rebuild.
  • The server decides it’s healthy. docker compose up -d --wait returns only when services are running or healthy, and fails otherwise (compose up). Then a request to /health through the proxy. Either failing restores the previous tag.

2. A workflow is a security boundary

The deploy job holds your SSH key; the build job holds a token that can push images. GitHub’s guide on secure use is the checklist (secure use):

  • Least privilege for GITHUB_TOKEN. A top-level permissions: { contents: read }, and packages: write only on the job that pushes (token permissions).
  • Pin actions to a commit SHA. Tags move. In March 2025, tj-actions/changed-files was compromised and its tags pointed at code that dumped secrets into logs (CISA alert). Workflows pinned to a SHA kept running the reviewed code. GitHub now also offers workflow dependency lockfiles, which pin transitive dependencies too and supersede SHA pinning where adopted.
  • No script injection. ${{ }} is replaced in the script’s text before bash runs it, so run: ./deploy.sh ${{ inputs.tag }} turns a crafted tag into code. Pass it through env: and use "$TAG": then it’s only ever data.
  • Verify the server. StrictHostKeyChecking=no means anyone who can redirect the connection receives your deploy, and your key. Store the server’s host key (from ssh-keyscan, checked by hand once) in a secret, and write it to known_hosts.
  • Never deploy from a pull request, and put the deploy job in a production environment, where secrets can be scoped and approvals required (environments).
  • Deploys queue, never overlap. One concurrency group, with cancel-in-progress: false: cancelling a deploy halfway can leave the server between versions.

3. Build the pipeline

The contracts are in the lab’s README.md. The checker runs deploy.sh against fake docker and curl that record every call and fail on demand, then lints deploy.yml with actionlint (which runs shellcheck on your scripts) and checks the security rules.

Start with set -euo pipefail, a cd to the script’s own folder, and the tag check with a regex ([[ $tag =~ ^[0-9a-f]{7,40}$ ]]). Make the six deploy.sh cases green, especially the two rollbacks.

Hint: set -e and the rollback

Under set -e, a failing command ends the script before your rollback runs. Put the risky part in an if: if TAG="$tag" docker compose … up -d --wait && curl -fsS …; then record; exit 0; fi, then roll back below it. Commands in an if condition don’t trigger set -e.

2

deploy.yml

Three jobs. Look up the real commit SHA of each action you use on its releases page (or with gh api repos/actions/checkout/commits/v4.2.2 --jq .sha), and keep the version in a comment: uses: actions/checkout@11bd719… # v4.2.2. Run until actionlint and every rule pass: all 15 cases.

Hint: one tag, two sources

In the deploy step: env: { TAG: ${{ inputs.tag || github.sha }} }, then ssh "deploy@$HOST" /srv/codearena/deploy.sh "$TAG". shellcheck warns (SC2029) that $TAG expands on the client: here that’s the point, and deploy.sh refuses anything but a SHA. Say so in a comment above # shellcheck disable=SC2029 (SC2029).

Challenge: a real rollback, timed

Once CodeArena deploys for real: push a commit whose API fails its health check on purpose, watch the pipeline roll back, and time how long the site was wrong. Then run the manual rollback with the tag input. Write both down: that’s the “rollback you’ve actually tried”.

4. What this means for CodeArena

  • Your CI already runs on pull requests (lint, typecheck, tests). The deploy workflow is a separate file that runs on main only.
  • Secrets: DEPLOY_SSH_KEY (a key made only for CI, in deploy’s authorized_keys), DEPLOY_KNOWN_HOSTS, DEPLOY_HOST, scoped to the production environment. The registry login uses the built-in GITHUB_TOKEN.
  • Each fix to the pipeline goes into the dojo’s team-workflow guide, part 14, like the others.

Your tokenizer is fast, and the people who need it write Python. Today you close that gap the way Hugging Face, Polars and Pydantic do: you compile the Rust into a Python extension module with PyO3, build and install it with maturin, and call it with import fasttok. Then you measure it against a pure-Python version of the same algorithm, and prove it lets other Python threads run while it works.

Why this matters

This is the concrete, defensible meaning of “Rust in AI”: Python stays the language people use, and the hot loop underneath moves to Rust. Being able to say “I wrote the core in Rust, exposed it with PyO3, and measured the speedup” is a rare and specific line on a CV.

1. How Python loads Rust

CPython can import extension modules: shared libraries (.so files on Linux) with a C interface and an init function. crate-type = ["cdylib"] asks Cargo for exactly that. PyO3 generates the C interface from Rust attributes and converts values at the boundary: a Python str arrives as &str, a list[int] as Vec<u32>, and a returned Vec<(u32, u32)> becomes a list of tuples (conversion tables). maturin builds the library and installs it: maturin develop into the active virtualenv, or maturin build --release into a wheel anyone can pip install (maturin guide).

2. A module in PyO3 0.30

#[pyo3::pymodule]
mod fasttok {                                  // the module Python imports
    use pyo3::prelude::*;

    #[pyclass]                                 // a Python class backed by a Rust struct
    struct Tokenizer { inner: crate::bpe::Tokenizer }

    #[pymethods]
    impl Tokenizer {
        #[staticmethod]
        fn train(text: &str, vocab_size: usize) -> Self { … }
        fn decode(&self, ids: Vec<u32>) -> PyResult<String> { … }   // Err → raises
        #[getter]
        fn merges(&self) -> Vec<(u32, u32)> { … }                    // tok.merges
        fn __len__(&self) -> usize { … }                              // len(tok)
    }
}

PyO3 0.30 declares a module as an inline mod (PyO3 guide); older tutorials show a function taking &Bound<PyModule>, which still works. Errors cross as exceptions: Err(PyValueError::new_err("…")) raises ValueError in the caller, so Result on the Rust side becomes try/except on the Python side.

3. The GIL, and letting go of it

CPython’s global interpreter lock lets one thread run Python at a time, and an extension holds it while it runs. For long work on Rust data, release it: py.detach(|| self.inner.encode(text)) runs the closure without the GIL, so other Python threads keep going (PyO3: parallelism). Inside the closure you mustn’t touch Python objects; for a call that takes microseconds, detaching costs more than it saves. PyO3’s docs also point to free-threaded Python, officially supported since 3.14, where there’s no GIL at all.

4. Build fasttok

Your lesson-40 tokenizer becomes src/bpe.rs, untouched. src/lib.start.rs declares the module and the class; you fill in five methods. check.sh creates a .venv the first time, installs maturin, runs maturin develop --release, then the Python tests: the same merges and tokens as tests/reference.py (pure Python), round trips, a ValueError on broken UTF-8, a speed comparison, and the GIL test.

1

Bring your tokenizer, write the class

cd ~/CODEARENA/apps/dojo/labs/0041-pyo3-extension
cp ../0040-bpe-tokenizer/src/lib.rs src/bpe.rs
cp src/lib.start.rs src/lib.rs
bash check.sh        # first run: venv, maturin, pyo3 (needs python3-venv)

Each method is one or two lines over self.inner. decode turns bytes into a String with String::from_utf8, and maps its error into a PyValueError. encode wraps its work in py.detach.

2

Use it from Python yourself

source .venv/bin/activate
python -c "import fasttok; t = fasttok.Tokenizer.train(open('tests/corpus.txt').read(), 400); print(len(t), t.encode('the judge'))"

Try a wrong type, t.encode(42), and read the TypeError PyO3 raises for you.

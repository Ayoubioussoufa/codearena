So far your runner limits how long a program runs and how much it prints. But the program still sees everything: your files, your processes, your network. Today you take that away. You’ll build the thing Docker builds for every container, in about 100 lines of C, and you won’t need root to do it.

Why this matters

Lesson 1 said a sandbox is a set of rules about what the kernel lets a program see and do. Namespaces are the “see” half. After today, “a container” stops being magic: it’s a process started with a few extra flags, and you’ll have written those flags yourself. Lesson 2’s escaper, the grandchild that left your process group, can’t escape what you build today.

1. A namespace is a private view

The kernel keeps some resources global: the hostname, the list of processes, the network interfaces, the mounted filesystems, the user IDs. A namespace gives a process its own copy of one of them. Everything else stays shared: same kernel, same CPU, same memory. Linux has eight kinds (namespaces(7)); you’ll use six:

CLONE_NEWUTSUTShostname

Try it (3 minutes). The unshare command creates namespaces for a shell. No sudo needed:

unshare --user --map-root-user --pid --fork --mount-proc --uts --net sh
hostname box; hostname       # changed... only in here
echo $$; ps                  # you're PID 1, and alone
ip link                      # just lo, and it's down
id -u                        # 0: root, in here
exit

Run hostname in another terminal: the host’s name didn’t change. That shell was a container in every sense except the files it could see. You’ll add those in section 4.

2. Root without power: the user namespace

Creating most namespaces needs root, with one exception: the user namespace. Any user can create one, and inside it the process can be uid 0, with all of root’s capabilities, but only over resources that belong to that namespace (user_namespaces(7)). Create the other namespaces together with a user namespace, and they belong to it. That’s how you’ll build a container without sudo.

Who is “root inside” on the outside? The kernel reads /proc/<pid>/uid_map, one line per range: inside-start outside-start count. Your box will use 0 1000 1: uid 0 inside is your own uid, 1000, outside. A file root creates inside belongs to you on the host, and the host’s files owned by real root stay out of reach.

Before writing gid_map, an unprivileged process must write deny to /proc/<pid>/setgroups: otherwise “root” inside could drop a group that was keeping it out of a file (user_namespaces(7), “Interaction with system calls that change process UIDs or GIDs”).

There’s a catch, and it shapes your code. A new user namespace starts with no mapping, and the child can’t write its own: the map has to be written from outside, by the parent. So the child must wait until the parent has written it. The classic tool is a pipe: the child reads from it, and the parent closes it once the maps are written.

3. PID 1 is special

The first process in a new PID namespace is its init, PID 1, and the kernel treats it differently in two ways (pid_namespaces(7)):

  • When PID 1 dies, the kernel kills every other process in the namespace with SIGKILL. No orphan survives, no matter what it did with setsid. That closes the hole lesson 2 left open: kill PID 1, and everything inside goes with it.
  • PID 1 only receives signals it has a handler for. Only SIGKILL and SIGSTOP sent from an ancestor namespace are forced through. A shell or a Node program running as PID 1 with no SIGTERM handler simply ignores SIGTERM.

The second rule is the rest of I-17. docker run forwards your SIGTERM to the container’s PID 1, and PID 1 ignores it, so nothing happens. Your checker proves it: inside your box, kill -TERM $$ followed by echo still alive prints still alive.

4. A filesystem of its own

A mount namespace gives the box its own mount table, but at first it’s a copy of yours: the same files. To give it different files, you need three moves.

  1. A root filesystem: a directory holding a whole Linux userland. The checker makes one by exporting Alpine’s from Docker (docker export of an alpine:3.20 container, about 8 MB).
  2. chroot(rootfs) makes that directory the process’s /. Then chdir("/"), or the current directory still points outside.
  3. The pseudo-filesystems. ps reads /proc, so mount a fresh proc there, which shows only your PID namespace. And programs expect /dev/null and friends, so mount a small tmpfs on /dev and bind-mount the host’s /dev/null, /dev/zero and /dev/urandom onto empty files in it. You can’t create device files in a user namespace, but you can bind existing ones: that’s what rootless container runtimes do.

First, though, call mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL), so your mounts stay in your namespace instead of propagating back to the host.

chroot isn’t a wall on its own. Its man page warns it “is not intended to be used for any kind of security purpose” (chroot(2)): a process with root’s powers can climb back out. Real runtimes use pivot_root, which swaps the whole root and lets you unmount the old one. That’s today’s challenge.

That directory is a whole Linux system’s files, and nothing else: no kernel, because the kernel is yours.

1

clone, a name, a PID

Start from lesson 1’s run.c shape, with clone instead of fork: CLONE_NEWUSER | CLONE_NEWUTS | CLONE_NEWPID | SIGCHLD. In fn, set the hostname and execvp the program. The parent waits and prints the status. The first two cases of “Its own names” should pass.

Why CLONE_NEWUSER already?

Without root, the kernel refuses CLONE_NEWUTS and CLONE_NEWPID on their own (EPERM). Created together with a user namespace, they belong to it, and the child has the capabilities to use them.

2

The uid map, and the wait

Make a pipe before clone. The child closes its write end, blocks on read until the parent is done, then carries on. The parent writes the three files under /proc/<child pid>/, then closes the pipe. “Its own root” should go green.

Hint: how the child knows the parent is done

It doesn’t need a message. Lesson 3: read returns 0, end of file, once every write end is closed. So the parent writes nothing into the pipe at all, and just closes it when the maps are written.

3

Its own files

Add CLONE_NEWNS. In the child, after the wait: make / private, set up /dev under the rootfs, chroot, chdir("/"), mount /proc, then exec. “Its own files” should go green, and so should the ps case: with its own /proc, the box sees one to three processes.

4

No network, and all green

Add CLONE_NEWNET | CLONE_NEWIPC, then run bash check.sh until all 13 cases pass. You didn’t write anything for “PID 1 is special”: the kernel did it. Read those two cases again until you can explain both.

★

Challenge: pivot_root, read-only

Replace chroot with pivot_root: bind-mount the rootfs onto itself (it must be a mount point), pivot_root(".", ".") from inside it, then unmount the old root with MNT_DETACH. Then make it read-only: remount the bind with MS_BIND | MS_REMOUNT | MS_RDONLY. Check by hand: ./build/box build/rootfs /bin/touch /etc/x must fail with “Read-only file system”.

6. What this means for a judge

  • This is what Docker does. docker run asks the daemon, which asks runc, which calls clone with these flags, sets up mounts and execs your program: what you wrote today, with more care.
  • PID namespaces close lesson 2’s hole. Kill PID 1, and nothing inside survives, whatever it did with process groups.
  • The user namespace is the one Docker skips. By default Docker doesn’t use one, so root in a container is root on the host, which is why your runner will add --user (lesson 8).
  • Seeing less isn’t using less. A box can still eat all your memory, fork a million processes, or spin on every core. Limits are lesson 6.

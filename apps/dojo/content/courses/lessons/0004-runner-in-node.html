CodeArena’s worker isn’t written in C. It’s TypeScript, running on Node. Today you rebuild your runner in Node, and see that every system call from lessons 1 to 3 is still there, hidden behind events and streams. You’ll also meet the Node defaults that look helpful and would quietly break a judge.

Why this matters

In lesson 8, CodeArena’s DockerCodeRunner will be spawn("docker", [...]) with this lesson’s runner wrapped around it. Every mistake here becomes a production bug there: a worker that crashes on one submission, a verdict that waits forever, a timeout that leaves processes behind. You’ll make some of those mistakes today, on purpose, in a lab where the checker catches them.

1. The same system calls, behind events

Node doesn’t have different powers from C. Its I/O library, libuv, makes the same system calls you made by hand. What changes is how you hear about the results: instead of blocking in waitpid, you get an event when something happens, and your code runs in between. Here’s everything you built, translated:

The exec/execFile functions in Node are not execvp: they’re spawn plus “collect all the output into one string”. Same word, different thing.

2. Four events, and the one to wait for

A child process in Node is an object that emits events:

  • 'spawn': the program started.
  • 'error': it couldn’t be started (or killed). For a missing program, this is all you get.
  • 'exit' (code, signal): the process ended. Its pipes may still hold unread output.
  • 'close' (code, signal): the process ended and all its stdio streams are closed. Wait for this one, or you’ll miss the last chunk of output.

Try it (2 minutes):

node -e '
const { spawn } = require("node:child_process");
for (const cmd of ["sh", "./no-such-program"]) {
  const c = spawn(cmd, ["-c", "echo hi; exit 3"]);
  for (const ev of ["spawn", "error", "exit", "close"])
    c.on(ev, (...a) => console.log(cmd, ev, a.map(String).join(" ")));
  c.stdout.on("data", (d) => console.log(cmd, "data", JSON.stringify(String(d))));
}'

For sh: spawn, data, exit, close, possibly in a slightly different order. For the missing program: an 'error' with ENOENT, then a 'close' with the odd code -2 (that’s -ENOENT), and no 'exit' at all. That’s the 127 of lesson 1, arriving by a different door, and it’s why a runner must resolve exactly once.

Remember lesson 3’s rule: a reader sees end of file only when every copy of the write end is closed. If an orphan still holds the child’s stdout, 'close' never fires.

There’s a trap in 'close', and it’s lesson 3’s rule again. It waits for every copy of the pipes to close, and a grandchild that inherited stdout holds a copy. Kill only the direct child, and 'close' waits for the orphan, maybe forever. When this lesson’s checker was tested with a runner that killed only the direct child, run() simply never answered. Killing the whole group at the deadline is what makes 'close' arrive.

3. Streams, and the event loop

In C, reading while the program runs took poll() and a loop. In Node, it’s the default. The event loop asks the kernel which pipes have data (with epoll on Linux, a bigger cousin of poll: see libuv’s design overview), reads them, and hands you each chunk in a 'data' event. That solves lesson 3’s deadlock, on three conditions:

  1. Read both streams. If nobody listens to stderr, Node stops draining it once its own buffer is full. The pipe fills, and the child blocks in write: lesson 3’s deadlock through the side door.
  2. End stdin. Write the input, then call child.stdin.end(). Without it, a program reading to end of file waits forever.
  3. Expect EPIPE. If the program exits without reading all its input, your next write fails with EPIPE. On a Node stream, that’s an 'error' event, and an 'error' event with no listener is thrown as an uncaught exception. One submission crashes your whole worker.

Try it (2 minutes). Condition 1, broken on purpose:

node -e '
const { spawn } = require("node:child_process");
const c = spawn("python3", ["-c", "import sys; sys.stderr.write(\"e\" * 200000); print(\"done\")"]);
c.stdout.on("data", (d) => console.log("stdout:", String(d).trim()));
setTimeout(() => { console.log("still running after 2 s:", c.exitCode === null); c.kill("SIGKILL"); }, 2000);'

“done” never prints: Python is stuck writing stderr that nobody reads. Add c.stderr.on("data", () => {}); and it finishes at once.

Collect output as Buffer chunks and decode once at the end. A UTF-8 character can be split across two chunks, and decoding each chunk separately would mangle it.

4. Node’s defaults are not a judge’s defaults

Node’s child-process options are designed for trusted programs. For a stranger’s code, three of them are traps:

  • The timeout option sends killSignal, which is SIGTERM by default (ignorable), and only to the direct child, not its group. That’s both of lesson 2’s traps in one option. When this lesson was tested, a shell killed this way left its sleep running.
  • exec and execFile collect all output in memory, up to maxBuffer (1 MiB by default), then kill the child with SIGTERM. You can’t stream, you can’t cap stdout and stderr your own way, and the kill is the polite one.
  • shell: true, and exec with a string, run your command through /bin/sh -c. Build that string from anything a user controls, and a filename like x; rm -rf ~ runs as a command. This is shell injection. A judge treats submitted code as data (a file, or stdin), and passes arguments as an array, never as one string.

So you write the deadline yourself: { detached: true } makes the child “the leader of a new process group and session” (Node docs), and at the deadline, process.kill(-child.pid, "SIGKILL") reaches every process in it.

detached also means the group outlives your worker if the worker dies. In lesson 8, the worker kills its running groups when it shuts down.

Before you build it, predict it. Unread streams, EPIPE and three ways to kill: say what each runner would report, with new scenarios every round.

5. Build: runner.mjs

The contract is in runner.start.mjs, as JSDoc types. In short:

run({ command, args, input, timeoutMs, maxOutputBytes }) → Promise<{
  outcome: "exit" | "signal" | "timeout"
         | "output-limit" | "spawn-error",
  exitCode, signal, stdout, stderr, timeMs
}>
  • It never rejects. A program that can’t start, crashes, hangs or floods is a fact, not an exception.
  • exitCode is set only for "exit", and signal (like "SIGSEGV") only for "signal".
  • stdout and stderr each keep at most maxOutputBytes bytes, and going over means "output-limit". If a limit stopped the program, the outcome is the first limit it hit.
  • At the deadline or the limit, the program and everything it started are killed.

Collect stdout and stderr, write the input and end stdin, and survive EPIPE. Make “Input and output” green, including the case where the program exits without reading 1 MB of input: the checker catches the uncaught exception that would have killed your worker.

The deadline

Spawn the program as the leader of its own group, set a timer, and at the deadline kill the whole group. Clear the timer when the run ends. Make “The deadline” green: a loop, a program that ignores SIGTERM, and two shells whose children must not survive.

Your run() never answers on the shell cases?

Then you killed only the shell. Its sleep is an orphan that still holds a copy of stdout, so 'close' waits for it (section 2). Kill -child.pid, not child.pid, and spawn with detached: true, or there’s no group to kill.

4

The cap

Count bytes per stream. Keep at most the cap; past it, record "output-limit" and kill the group. Exactly the cap must still pass. Then run bash check.sh until all 18 cases are green.

Hint: “the first verdict wins”, in one operator

Keep a verdict variable that starts as null. The timer does verdict ??= "timeout", and the cap does verdict ??= "output-limit". ??= only assigns if it’s still null, so whichever limit was hit first is what you report: the thing that actually stopped the program.

6. What this means for a judge

  • The worker must survive every submission. Unhandled 'error' events, unread streams and orphans holding pipes are worker bugs that look like user bugs.
  • Never trust a convenience option with a stranger’s code. timeout, exec, maxBuffer and shell are built for programs you trust.
  • Facts out, verdicts later. Your run() returns what happened, not whether the answer was right. Turning facts into AC, WA or TLE is the judge loop’s job (lesson 9).
  • In Docker, the group isn’t enough. spawn("docker", …) starts a client, and killing its group kills the messenger (lesson 2, I-17). The DockerCodeRunner will also kill the container by name.

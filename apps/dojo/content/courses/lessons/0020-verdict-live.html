The user clicks Submit and sees PENDING. A few seconds later, a worker in another process writes the verdict to the database. How does a page that’s already loaded find out? Either the browser keeps asking, or the server tells it. Today you build both, and you learn the two bugs that make live features flaky: requests that pile up, and updates that fall between two lines of code.

Why this matters

This afternoon’s task is the live verdict: polling first, then push if you choose. The test that’s already in your plan, “polling stops once a verdict arrives (no request after it)”, is one of the cases you’re about to make pass by hand.

1. Polling, done properly

Polling is the simplest live feature: ask GET /submissions/:id again and again until the status is final. Five details separate a polling loop that behaves from one that hurts:

  1. One request at a time. Schedule the next request with setTimeout after each answer, not with setInterval, which fires whether the last answer came back or not. A slow API then gets more requests, exactly when it can least afford them.
  2. Stop on the verdict. No request after the final state.
  3. Stop on unmount. The user navigates away: an AbortSignal ends the loop, or it keeps polling for a page nobody is looking at.
  4. Give up eventually. A judge that never answers shouldn’t leave a spinner forever: time out, and show a message.
  5. Survive a blip, with a limited number of retries.

In CodeArena you won’t write this loop. TanStack Query runs it when refetchInterval is a function of the latest data: return a number to keep polling, false to stop (useQuery reference):

useQuery({
  queryKey: ["submission", id],
  queryFn: () => api.getSubmission(id),
  refetchInterval: (query) =>
    query.state.data?.status === "DONE" ? false : 1000,
});

The cost is simple to compute: 1,000 users waiting, polling every second, is 1,000 requests a second, nearly all answering “still PENDING”. Fine at CodeArena’s size. Not at a much larger one.

2. Push: server-sent events

With server-sent events, the browser makes one request and the server keeps the response open, writing an event whenever something changes. On the wire it’s plain text with the type text/event-stream (MDN: using server-sent events):

event: status
data: {"id":"7","status":"RUNNING"}

: ping

event: status
data: {"id":"7","status":"DONE","verdict":"ACCEPTED"}
  • A blank line ends an event. A line starting with : is a comment: servers send them as heartbeats, because proxies close connections that stay silent too long.
  • The browser side is new EventSource(url), which reconnects by itself after a drop.
  • Without HTTP/2, a browser allows only 6 open SSE connections per domain, across all its tabs, as MDN warns. Behind an HTTP/2 proxy, that limit goes away.

WebSockets are the other push channel: a full two-way connection after an HTTP upgrade (MDN: WebSockets). Worth it when the browser talks back continuously, like a chat. A verdict only flows one way, so SSE is the simpler tool.

3. The race that loses verdicts

An SSE handler needs two things: the submission’s current state (it may already be judged), and every change after it. Read first, then subscribe, and there’s a gap: a verdict published after your read but before your subscription reaches nobody. The page shows RUNNING forever. It only happens when timing is unlucky, so it passes every manual test and fails in production.

The fix is to subscribe first, buffer, then read: everything published after the subscription is caught, and the worst case is seeing a state twice, which you filter out. The same thinking applies to where the events come from. In CodeArena, the worker and the API are separate processes, so the worker publishes on a Redis channel after the database commit. Redis Pub/Sub is at-most-once: a message published while nobody is subscribed is gone (Redis: Pub/Sub). That’s acceptable only because the database stays the truth, and every client starts by reading it.

2

The SSE endpoint

Subscribe to the bus, then read the store, then write the headers, the current state, and any buffered events. End after DONE; ping on a timer; on req’s "close", remove the listener and the timer. All 14 cases should pass.

Challenge: resume with Last-Event-ID

Give each event an id: line. When EventSource reconnects, it sends the last id it saw in a Last-Event-ID header (the SSE standard). Use it to skip the states the client already has.

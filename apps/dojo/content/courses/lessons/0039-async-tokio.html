Threads are the right tool when work needs cores. When work mostly waits (for a socket, a timer, a container to finish), a thread per wait is wasteful: each one reserves a stack and the OS has to schedule it. Async Rust turns each waiting job into a small state machine, and a runtime, tokio, drives thousands of them on a few threads. Today you build a job runner with a concurrency limit and per-job timeouts, race two mirrors, and meet the one mistake that makes async slower than threads.

Why this matters

Nearly every Rust network service runs on tokio: web frameworks like axum, database clients, proxies. And you already know the model from Node’s event loop, with one difference that bites people: a Rust future does nothing until it’s polled.

1. Futures are lazy, and .await yields

async fn wait(ms: u64) {
    tokio::time::sleep(Duration::from_millis(ms)).await;
}
let f = wait(100);      // builds a future: nothing has run
f.await;                // now it runs; while it sleeps, the thread serves other tasks

An async fn returns a future, a state machine the compiler writes for you, and its body doesn’t start until something polls it: .await, join!, select!, or tokio::spawn (tokio tutorial: Hello Tokio). That’s the opposite of a JavaScript promise, which starts running as soon as it’s created. At an .await on something not ready, the task gives its thread back, and the runtime wakes it when the timer fires or the socket has data.

A future that loses a select! or a timeout is dropped: it never runs again, so it’s cancelled at the .await where it was waiting (tokio tutorial: select). A semaphore permit is released when its guard drops, which is lesson 29’s ownership doing concurrency control: hold _permit for the length of the job.

3. Never block the runtime

Scheduling is cooperative: a task gives up its thread only at an .await. A CPU loop or a blocking call inside an async function (std::thread::sleep, a big compression, a synchronous C library) holds the thread, and every task scheduled on it waits. tokio::task::spawn_blocking(move || work()) runs the closure on a separate pool of threads meant for blocking, and gives you a future for the result. tokio’s own tutorial says when not to use it at all: CPU-bound computation (use rayon), reading many files, or a single request where the blocking library is simpler (tokio tutorial).

4. Build the runner

run_all runs jobs (each a sleep, standing in for I/O) with a semaphore limit and a timeout per job; fastest races two mirrors with select!; checksum_all runs slow_checksum (300 ms of blocking work, given in kit.rs) without blocking the runtime. Most tests run on tokio’s paused clock (start_paused = true, from the test-util feature): sleeps finish instantly, and elapsed time is exact. 100 one-second jobs, 10 at a time, must take exactly 10 virtual seconds.

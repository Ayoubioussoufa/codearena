Once CodeArena runs on a server, you can’t attach a debugger or read the console. Everything you’ll ever know about production comes from what it writes down: logs, metrics and health checks. Then there’s the one thing that saves you when all of it is too late: a backup you know works because you’ve restored it. Today you build all four, and you test the backup by destroying the data.

Why this matters

This afternoon’s task is structured logs, a health endpoint, metrics, error tracking and a nightly backup you’ve restored once. In an interview, “how would you know it’s broken before users tell you?” separates someone who has run software from someone who has only written it.

1. Logs: events you can search

A log line is an event: one request, one failure. Write it as one JSON object per line, and “every 500 on /submissions in the last hour” becomes a query on fields instead of a fragile regex (wrapped here to fit the page; in the log it’s one line):

{"time":"2026-11-20T14:02:11.402Z","level":"error","msg":"request",
 "method":"POST","path":"/submissions","status":500,"durationMs":31.2,
 "requestId":"9f1c…","error":"connect ECONNREFUSED"}
  • A request id ties every line about one request together, across the proxy, the API and the worker. Accept one from upstream if it looks sane, otherwise make one, and send it back in a header so a user can quote it.
  • Never log secrets. Tokens hide in query strings and the Authorization header; cookies hold sessions. Logs travel further than your database ever will, and OWASP lists access tokens and session identifiers among what must never be logged (Logging Cheat Sheet).

2. Health: alive, or ready?

Two different questions (Kubernetes: probes):

  • Liveness, /health: can this process still answer? If not, restart it.
  • Readiness, /ready: can it do useful work right now, with its database and Redis answering? If not, stop sending it traffic, but don’t restart it: a restart won’t fix Postgres.

Every check needs a timeout: a dependency that hangs is down, and a readiness check that hangs with it is worse than none.

3. Metrics: numbers over time

Logs answer “what happened to this request?”. Metrics answer “how is the system doing?”: counters and histograms that a server like Prometheus scrapes every few seconds from /metrics, in a plain text format (exposition formats):

# TYPE http_requests_total counter
http_requests_total{method="POST",route="/submissions",status="202"} 1027
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{method="POST",route="/submissions",le="0.1"} 990
http_request_duration_seconds_bucket{method="POST",route="/submissions",le="+Inf"} 1027
http_request_duration_seconds_sum{method="POST",route="/submissions"} 41.7
http_request_duration_seconds_count{method="POST",route="/submissions"} 1027
  • Histogram buckets are cumulative: le="0.1" counts every request that took 0.1 s or less (histograms). From them, Prometheus estimates percentiles like p95 latency.
  • Watch your labels. Every distinct combination of label values is a separate series, kept in memory. Use the route template, never the raw path; never a user id (naming and labels). One scanner trying 10,000 random URLs shouldn’t create 10,000 series.
  • What to measure first: Google’s SRE book names four golden signals: latency, traffic, errors and saturation (monitoring distributed systems). For CodeArena, add the queue: how many jobs are waiting, and how old the oldest is.

Error tracking (Sentry, for instance) groups exceptions with their stack traces and tells you when a new one appears (Sentry for NestJS). It complements logs: a log line says a 500 happened, the error tracker shows the line of code.

4. Backups: only a restore proves one

pg_dump --format=custom writes an archive that pg_restore can read selectively (pg_dump). Run it nightly, keep a week, and copy it off the server: a backup on the same disk dies with the disk. Then the part almost everyone skips: restore it, into a scratch database, and count something you know. A dump can be empty, truncated or unrestorable, and the only way to find out is to try, before the day you need it.

6. What this means for CodeArena

  • Logs: nestjs-pino in the API, the same JSON shape in the worker, with the submission id on every judging line.
  • Health: /health for Docker’s health check and Compose’s --wait; /ready for the proxy and for you.
  • Metrics and alerts: requests and latency per route, verdicts by type, queue depth, judge duration. Alert on symptoms users feel: errors and latency, a queue that keeps growing.
  • Backups: a nightly cron on the VM running your script, a copy off the server, and the restore check on a schedule.

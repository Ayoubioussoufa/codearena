Lesson 13 ended with an honest promise: a queue that survives crashes delivers each job at least once. Sometimes twice. Today you make the second delivery harmless, with a technique that also fixes I-6, the race in your refresh tokens: one statement that checks and writes at once.

Why this matters

“The same job delivered twice judges once, and here’s the test that proves it, even concurrently” is the second-best sentence in your interview after the sandbox. The idea is called idempotency: doing something twice has the same effect as doing it once. Stripe built their API around it (Stripe: designing robust and predictable APIs with idempotency).

1. Check-then-write is a race

The obvious claim reads the submission, sees PENDING, then updates it to RUNNING. Two workers that both read before either writes both see PENDING, and both run it. That’s exactly I-6: two concurrent refreshes both find the token unused.

The fix is to put the check inside the write:

UPDATE submissions
SET status = 'RUNNING', claimed_by = $worker, claimed_at = now()
WHERE id = $id AND status = 'PENDING'
RETURNING id;  -- a row back: you won. Nothing back: someone else did

Why is that safe? The first UPDATE locks the row. The others wait, and when it commits, each one re-evaluates its WHERE against the new version of the row (Postgres: Read Committed). The row says RUNNING now, so nothing matches, nothing is written, and no row is returned. This is a compare-and-set. In Prisma it’s updateMany with the condition in where, then checking count === 1.

2. Claims that expire, and fencing

A claim held by a dead worker blocks the submission forever. So a claim gets a lease: it can be taken over once claimed_at is older than some duration, by adding OR (status = 'RUNNING' AND claimed_at < now() - lease) to the condition.

That opens a subtler hole. The old worker may not be dead, only slow. If it finishes after the new owner, it overwrites a newer verdict. So every write after the claim must also be conditional on still holding it (AND claimed_by = $worker). That’s called fencing, and Martin Kleppmann’s article on distributed locks explains why a lease without it isn’t safe (How to do distributed locking).

Kleppmann’s stronger version is a fencing token: a number that increases with every claim, checked on every write. A worker id works when ids are unique per claim; the token works even if the same worker claims twice. That’s the challenge.

3. Retries, and the end of the line

  • Retry your failures, not the user’s. Docker or Postgres down: retry with exponential backoff (wait 1 s, 2 s, 4 s…) so a struggling service isn’t hammered. A verdict is a successful job, never retried.
  • Never leave a submission in PENDING forever. After the last retry, give it a terminal state the user can see (an internal error with a “try again”), keep the job in the dead-letter queue, and alert.
  • BullMQ’s side: attempts and backoff on the job, and a failed event after the last one (retrying failing jobs). Throwing in the processor means “retry me”; returning normally means done, whatever the verdict.

5. What this means for CodeArena

  • The idempotency test delivers the same job twice, also concurrently, and asserts the runner was called once and one verdict written: use the fake runner and count its calls.
  • The claim lives in the worker, the condition in the database. No in-memory lock survives two worker processes.
  • The lease must outlast a run. Pick it from your time limits (all tests, plus startup), or renew it while judging.

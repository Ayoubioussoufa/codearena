Your box from lesson 5 sees almost nothing, but it can still use everything: allocate all your memory, start processes until the machine chokes, keep every core busy. Today you put a ceiling on all three, and the kernel enforces it. You do it by writing numbers into files.

Why this matters

Memory Limit Exceeded is a verdict, and so is the fork bomb a stranger will submit on day one. Today’s tool, the cgroup, decides both, and gives you a third fix for lesson 2’s escaper: one write to cgroup.kill stops every process in the box, whatever group or session it ran off to.

1. A cgroup is a directory

A control group is a set of processes that the kernel accounts for, and limits, together. In cgroup v2 they form one tree, and the tree is a filesystem: every cgroup is a directory under /sys/fs/cgroup, and everything about it is a file (the kernel’s cgroup v2 documentation):

  • cgroup.procs lists the processes in it. Write a PID there, and that process moves in.
  • Controllers (memory, pids, cpu…) are switched on for a cgroup’s children in its cgroup.subtree_control.
  • Limits are files you write: memory.max, pids.max, cpu.max.
  • Results are files you read: memory.events, pids.events, cpu.stat.

Children inherit their parent’s cgroup at fork, so moving one process into a cgroup before exec puts everything it ever starts in there too. Lesson 1 said where that move goes: the gap.

Try it (3 minutes). See where your shell lives, then let systemd set a memory limit for you:

cat /proc/self/cgroup
systemd-run --user --scope --quiet -p MemoryMax=50M -p MemorySwapMax=0 \
  python3 -c "b = bytearray(200 * 1024 * 1024); print('allocated')"
echo "exit=$?"

No “allocated”: Python is killed, and the exit code is 137. That’s the OOM killer, inside the cgroup systemd created and wrote memory.max for. Today you write that file yourself.

2. Three limits, three behaviours

The three limits a judge needs do three different things when they’re hit, and the difference matters for your verdicts:

WriteWhen it’s hitRead afterwards
memory.max (and memory.swap.max = 0)the OOM killer kills a process in the cgroup: SIGKILLmemory.events, line oom_kill
pids.maxfork fails with EAGAIN. Nothing diespids.events, line max
cpu.max: "quota period" in µsthe program is throttled: it waits for the next period. Slower, never killedcpu.stat, line usage_usec

Linux hands out memory lazily, so malloc(4 GB) usually succeeds. The kill comes when the program touches the pages. That’s why the lab’s hog writes to every byte it allocates.

Two consequences. A fork bomb doesn’t get killed, it just stops growing, so your runner must still clean up. And a CPU limit is not a time limit: cpu.max at 25% makes a program four times slower, and only your wall-clock deadline from lesson 2 stops it. What cpu.stat gives you is the fair number to report as the run’s time: CPU time, the same on a busy machine as on an idle one.

3. Who may write where: delegation

The cgroup tree belongs to root. But systemd delegates a subtree to each logged-in user: under /sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/, the files are yours. Run a command with systemd-run --user --scope -p Delegate=yes, and it starts in a fresh cgroup of its own, inside that subtree, with the memory, pids and cpu controllers available. That’s where your cage will work, with no sudo.

One rule shapes your code: no internal processes. A cgroup that hands controllers down to its children can’t hold processes itself (“No Internal Process Constraint”). Your cage starts inside its scope, so before enabling controllers it must move itself into a leaf. The usual name for that leaf is supervisor, and the box gets a sibling leaf of its own:

run-….scope/                # your scope: no processes left here
├── cgroup.subtree_control  # "+memory +pids +cpu"
├── supervisor/             # cage itself, moved here first
└── box-4120/               # the program: memory.max, pids.max, cpu.max

And the cleanup tool: writing 1 to a cgroup’s cgroup.kill SIGKILLs every process in it at once, including ones that called setsid. Membership in a cgroup can’t be escaped by changing groups or sessions, because it isn’t a group or a session. That’s the third way to close lesson 2’s hole, after process groups (which fail) and PID namespaces (lesson 5).

4. Build cage

Usage: ./cage [-m bytes] [-p pids] [-c percent] <program> [args...]

Runs the program in a new cgroup with the limits asked for (none if a flag is absent), then kills anything left in it, and prints four lines after the program’s own output:

exit N            # or: signal S
oom_kills=N
pids_refused=N
cpu_ms=N

A value that isn’t a positive number, or no program: a usage line on stderr, exit 2. The checker runs your cage with systemd-run --user --scope -p Delegate=yes, plus a safety net of 300 processes, so even a cage with a broken pids.max can’t hurt your machine.

The write to cgroup.subtree_control fails?

EBUSY means a process is still in the cgroup: did you move yourself to supervisor first? ENOENT means a controller you named isn’t available there: check cgroup.controllers. Print errno with perror: the kernel tells you which.

5. What this means for a judge

  • Docker’s flags are these files. --memory and --memory-swap write memory.max and memory.swap.max; --pids-limit writes pids.max; --cpus writes cpu.max. Lesson 8 maps every flag.
  • MLE is a fact, not a guess. An OOM kill and your own deadline both end in SIGKILL; only the cgroup’s oom_kill counter tells them apart.
  • Report CPU time, enforce wall time. cpu.stat is the fair runtime; lesson 2’s deadline is what stops a sleeper.
  • Clean up by cgroup. Killing by membership is the one kill nothing can dodge.

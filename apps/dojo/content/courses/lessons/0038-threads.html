A judge spends most of its time waiting for programs to finish, so it runs several at once. In C or TypeScript you’d protect shared state by discipline and code review. In Rust, the borrowing rule you learned in lesson 30, one writer or many readers, holds across threads too, and a data race is a compile error. Today you plant one, watch it refused, then judge in parallel two ways: scoped threads that borrow, and a worker pool fed by a channel.

Why this matters

“Fearless concurrency” is the Rust slogan, and an interviewer will ask what it really means. After today you can say it precisely: which bugs the compiler rules out (data races), which it doesn’t (deadlocks, a wrong worker count), and which two traits, Send and Sync, carry the proof.

1. Two ways to start a thread

// thread::spawn: the thread may outlive this function, so it must own its data
let h = thread::spawn(move || judge_one(&job));    // move: the closure takes `job`
let outcome = h.join().unwrap();                    // join: wait, and get its result

// thread::scope: every thread ends before the scope does, so they may borrow
thread::scope(|s| {
    for chunk in jobs.chunks(size) {
        s.spawn(move || chunk.iter().map(judge_one).collect::<Vec<_>>());
    }
});                                                 // all joined here

thread::spawn requires a 'static closure: it owns everything it uses, or shares it through an Arc. thread::scope (stable since Rust 1.63) lifts that requirement, because the scope can’t return before its threads have finished (std::thread::scope). A thread’s return value comes back through join(), and that’s often all the communication you need.

2. The data race that doesn’t compile

let mut total = 0;
thread::scope(|s| {
    for chunk in values.chunks(1000) {
        s.spawn(|| total += chunk.iter().sum::<u64>());   // E0499
    }
});

Each closure needs &mut total, and two can’t exist at once. That rule is exactly the definition of a data race (two threads, one location, at least one writing, no synchronization), so data races can’t compile. The fixes all remove the shared &mut: return partial sums through join; use an AtomicU64; or wrap the value in a Mutex, which hands out one &mut at a time.

3. Send, Sync, and the shared-state toolbox

Two marker traits carry the proof. A type is Send if it can move to another thread, and Sync if &T can be shared between threads. The compiler derives both from a type’s fields (The Book, §16.4). Rc isn’t Send (its count isn’t atomic), RefCell isn’t Sync (its borrow flag isn’t either), so using them across threads is E0277.

Rust rules out data races, not deadlocks: two threads that each hold one lock and wait for the other’s hang forever in perfectly safe code, as The Book warns (§16.3).

The channel pool

Two channels: jobs out, outcomes back. The job receiver can’t be cloned, so share it as Arc<Mutex<Receiver<Job>>>; each worker locks, recv()s one job, unlocks (the guard drops at the end of the statement), judges. Workers stop when recv() returns Err, which happens once every sender is dropped, so drop yours after sending. Drop your copy of the outcome sender too, or the collecting loop never ends.

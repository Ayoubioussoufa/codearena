A judge reads a submission, compiles it, and runs it against every test. For each test it feeds the input, waits for the program to finish, reads what the program printed, and compares that output with the expected answer. If the program prints the right answer for every test, the submission is accepted. If it prints a wrong answer, runs too long, uses too much memory, or crashes, the judge reports the first test that failed and stops there, because running the remaining tests would only cost time.

The judge must never trust the program. The program might loop forever, so the judge sets a deadline and kills it when the deadline passes. The program might print forever, so the judge reads at most a fixed number of bytes and kills it when the cap is reached. The program might start other programs, so the judge kills the whole process group, not only the first process. The program might try to read files, open sockets or fill the disk, so the judge runs it inside a container with no network, a read-only file system and strict limits on memory and processes.

A contest adds a clock and a scoreboard. Teams submit solutions while the contest runs, and the scoreboard ranks them by the number of problems solved, then by penalty time. Every accepted submission adds the minute it was accepted, plus twenty minutes for every rejected submission before it on the same problem. Rejected submissions on a problem that is never solved cost nothing. In the last hour the scoreboard is frozen, so the final ranking is revealed only after the contest ends.

A practice platform adds memory of what each person has solved. It schedules problems again just before they would be forgotten, it picks the next problem at the edge of what the person can do, and it explains each verdict in words a beginner can act on. The judge stays the same: it reads, compiles, runs, compares, and reports, test after test, submission after submission, all day long.

In a Next.js app, the same .tsx file can run on the server, in the browser, or both, and the code never says which out loud. Today you take the mystery out by building the machine yourself: a renderer that turns a component tree into HTML, decides which pieces the browser must download, and packs what it needs to bring them to life. Why this matters

This afternoon you build the problem page and the submit form. “Which parts are server components, and why?” is the first decision, and it’s a classic interview question for any React role. Get it right, and the page loads fast, ships little JavaScript, and never leaks a secret.

The idea of pages as static HTML with a few interactive islands predates React’s version of it (patterns.dev: islands architecture). React Server Components make it the default.

2. Server components, client components, and the payload

  • Server components are the default in the App Router. They run only on the server, can be async, can read the database and secrets directly, and their code never reaches the browser (Next: server and client components).
  • 'use client' marks a boundary. That file, and everything it imports, becomes client code. Client components still render on the server for the first HTML; then the browser downloads their code and hydrates them. That’s where useState, effects, event handlers and browser APIs can live.
  • The RSC payload is what crosses: the rendered server output, plus, for each client component, which one it is and its props. The browser uses it to hydrate and, on navigation, to update the page without a full reload.

Every rule you’ll meet follows from that payload:

  • Props from server to client must be serializable. React can carry plain objects, arrays, Date, Map, Set, promises and JSX, but not ordinary functions or class instances (React: serializable types). Your lab keeps JSON’s stricter rules.
  • A client component can’t import a server component, since its code would have to run in the browser. A server component can pass one in as children: it renders on the server, and the client component receives the result.
  • Anything a client component receives ships. Pass the whole problem to a client component, and the statement crosses twice: once as HTML, once in the payload. Pass it a secret, and the secret is in the page.

Two safety nets in Next: only environment variables prefixed with NEXT_PUBLIC_ are inlined into client code (environment variables), and importing the server-only package in a module makes any client import of it a build error.

3. One more danger: the payload is inside your HTML

The payload travels as JSON in a <script> tag. If a prop contains </script><script>alert(1)</script> and you paste the JSON in as is, the browser ends your script at the first </script> and runs the attacker’s. That’s a stored XSS from a problem title. The fix is to write every < in the JSON as <: still valid JSON, and it can no longer close a tag. Frameworks do this for you; your renderer will too.

5. In Next, the same decisions

  • Push 'use client' down to the leaves. The page and the statement stay server components; the editor and the submit form are small client components that receive only what they need (problemId, the starter code).
  • Fetch on the server when you can. An async server component awaits the problem; no loading spinner, no request waterfall in the browser.
  • Mutations are client-side here. The submit form uses a TanStack Query useMutation to POST /submissions, shows the API’s validation message, then navigates to the submission page.

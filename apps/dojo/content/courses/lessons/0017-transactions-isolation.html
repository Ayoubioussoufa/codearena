A transaction is a promise that a group of statements happens all or nothing. It is not a promise that concurrent transactions can’t trip over each other. How much they can is set by the isolation level, and the default lets more through than most developers think. Today you watch each race happen with your own hands, in two terminals, then fix the one CodeArena has.

Why this matters

When a verdict is Accepted, the worker records the solve and bumps the user’s score. Two deliveries of the same job (lesson 13), or two Accepted submissions for the same problem, arrive together: is the solve counted twice? This afternoon you pick the mechanism, write the test, and justify the level in an ADR.

1. Three levels, one question: what does a statement see?

Postgres keeps several versions of each row (that’s MVCC), so a reader never waits for a writer. Each statement reads from a snapshot: the database as of some moment. The isolation level decides which moment (transaction isolation):

LevelSnapshotWrites that conflict
READ COMMITTED (the default)a new one for each statementwait for the lock, then re-check the row’s newest version
REPEATABLE READone for the whole transactionupdating a row changed since your snapshot fails: retry
SERIALIZABLEone for the whole transactionalso fails whenever the result couldn’t have come from running the transactions one at a time

The pattern: stronger levels don’t make races disappear by magic. They turn them into errors you retry. Weaker levels let them through as wrong data.

A

A non-repeatable read

-- T1 and T2 are your two terminals; run the lines top to bottom
T1  BEGIN;
T1  SELECT solved FROM users WHERE id = 3;      -- 0
T2  UPDATE users SET solved = 5 WHERE id = 3;
T1  SELECT solved FROM users WHERE id = 3;      -- ?
T1  COMMIT;

Predict the second read, then run it. Reset, and do it again with BEGIN ISOLATION LEVEL REPEATABLE READ;. Same transaction, two different answers: that’s why reports and anything that reads twice want a single snapshot.

B

Two increments: the lock, then the failure

T1  BEGIN;
T2  BEGIN;
T1  UPDATE counters SET n = n + 1 WHERE id = 1;
T2  UPDATE counters SET n = n + 1 WHERE id = 1;   -- waits…
T1  COMMIT;                                       -- …and T2 resumes
T2  COMMIT;
T1  SELECT n FROM counters;                       -- ?

Terminal 2 blocks on the row lock until terminal 1 commits, then re-reads the row and adds 1 to the new value. Now reset and do it with both sessions at REPEATABLE READ: terminal 2 gets could not serialize access due to concurrent update. Its snapshot is older than the row it wants to change, so it can’t safely continue.

C

Write skew: the race no row lock sees

T1  BEGIN ISOLATION LEVEL REPEATABLE READ;
T2  BEGIN ISOLATION LEVEL REPEATABLE READ;
T1  SELECT count(*) FROM users WHERE is_admin;    -- 2
T2  SELECT count(*) FROM users WHERE is_admin;    -- 2
T1  UPDATE users SET is_admin = false WHERE id = 1;
T2  UPDATE users SET is_admin = false WHERE id = 2;
T1  COMMIT;
T2  COMMIT;
T1  SELECT count(*) FROM users WHERE is_admin;    -- ?

Each checked “someone else is still admin”, each was right in its snapshot, and they wrote different rows, so nothing conflicted. Zero admins. Reset and redo it at SERIALIZABLE: the second COMMIT fails with could not serialize access due to read/write dependencies among transactions. Postgres tracked what each one read and saw the cycle.

This is write skew, from Martin Kleppmann’s Designing Data-Intensive Applications, chapter 7 (his example is two doctors going off call). Lesson 14’s claim and the starter in this lab are the same shape: check a condition, then write.

3. Three ways to make check-then-act safe

  1. One statement that checks and writes (lesson 14). SET n = n + 1, or a conditional UPDATE … WHERE. Cheapest; works at READ COMMITTED.
  2. A constraint that makes the second write impossible. A unique key on (user_id, problem_id) plus INSERT … ON CONFLICT DO NOTHING RETURNING (INSERT): the row that comes back tells you whether you were first. The database enforces it for every code path, forever.
  3. A lock, or SERIALIZABLE. SELECT … FOR UPDATE on a row everyone touches serializes them (explicit locking). Or keep the naive logic, run it at SERIALIZABLE, and retry on failure (serialization failure handling). That’s the most general tool, but every caller needs the retry loop.

5. What this means for CodeArena

  • Prefer the constraint. A unique key on the solve is enforced for every code path, including the ones you’ll write next year.
  • If you pick SERIALIZABLE, pass { isolationLevel: Prisma.TransactionIsolationLevel.Serializable } to $transaction, and retry on error code P2034: in CodeArena’s Prisma 7.8 with the pg adapter, that’s what SQLSTATE 40001 and deadlocks become. Retry the whole transaction, with a limit.
  • Test it concurrently. The test fires the same Accepted twice with Promise.all and asserts the score moved once. A sequential test can’t see a race.

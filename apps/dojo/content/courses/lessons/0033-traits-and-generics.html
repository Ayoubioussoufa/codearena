Lesson 9’s judge compared tokens, and its challenge mentioned problems that need another rule: a float answer within a tolerance, any valid path in a graph. In CodeArena you’d write an interface and a few classes. In Rust, the shared behaviour is a trait, each checker is a type that implements it, and you choose how calls are resolved: at compile time with generics, or at runtime with trait objects. Today you build both, and learn which to pick.

Why this matters

Traits are how Rust does everything you used interfaces and dependency injection for in NestJS, and how the standard library works: Display, Iterator, From, Send. “Static or dynamic dispatch?” is also a classic systems interview question, and after today you can answer it with numbers: one inlined call, or one pointer jump.

1. A trait is a promise

pub trait Checker {
    fn check(&self, expected: &str, actual: &str) -> bool;   // required
    fn name(&self) -> String;                                  // required
    fn failures(&self, cases: &[(&str, &str)]) -> Vec<usize> {
        // a default method: written once, in terms of check
    }
}
impl Checker for Tokens {
    fn check(&self, expected: &str, actual: &str) -> bool { /* … */ }
    fn name(&self) -> String { "tokens".to_string() }
}

A type implements a trait explicitly, with impl Checker for Tokens, like Java’s implements rather than TypeScript’s structural matching. There’s no inheritance of fields: data lives in structs, shared behaviour in traits (The Book, §10.2). You already implemented two standard traits in lesson 32, Display and From.

2. Generics: one copy per type

pub fn count_passed<C: Checker>(checker: &C, cases: &[(&str, &str)]) -> usize

C: Checker is a trait bound: any type, as long as it implements Checker. Inside, you may use only what the bound promises. The compiler then monomorphizes: it writes one copy of count_passed for each type you call it with, each calling its checker directly, so the optimizer can inline check into the loop (§10.1, “Performance of Code Using Generics”). Generic structs work the same way: IgnoreCase<C> wraps any checker, at no runtime cost.

3. Trait objects: one type for many

A problem’s config names its checker, so the type is only known at runtime, and a Vec of checkers would hold different types. Both need one type that stands for “some checker”: Box<dyn Checker>, a trait object. It’s two pointers, one to the value and one to a vtable (that type’s table of method addresses), and each call goes through the table: dynamic dispatch, as in C++ virtual calls (§18.2).

“What’s my rank among 50,000 users?” is a terrible question for a SQL table and a trivial one for a Redis sorted set. Today you learn why, build a leaderboard that is fair on ties and correct under duplicate deliveries, and meet a new idea that runs through all of system design: data you can throw away because you can rebuild it.

Why this matters

This afternoon’s task is the live leaderboard: the worker updates it on every Accepted, idempotently, and two endpoints read it. It’s also worked design #9 in your system-design guide. After today, the design and the code are the same thing.

1. Why not just Postgres?

SELECT … ORDER BY points DESC LIMIT 10 is fine with an index. The hard question is the other one: my rank. That’s “how many users have more points than me?”, a count over a large slice of the table, on every profile view. It gets slower as the board grows, and the board changes on every Accepted.

A Redis sorted set keeps members ordered by a score at all times. It’s a skip list (a sorted linked list with “express lanes” above it, so a search skips most of the elements) plus a hash table from member to score. Adding, updating and ranking are all O(log N); reading one score is O(1) (Redis: sorted sets).

ZINCRBY lb:board 100 ada             # ada +100, O(log N)
ZRANGE  lb:board 0 9 REV WITHSCORES  # the top 10, best first
ZREVRANK lb:board ada                # 0 for the best: add 1 for a rank
ZSCORE  lb:board ada                 # O(1)

ZREVRANGE, which you’ll see in older tutorials, is deprecated since Redis 6.2: use ZRANGE … REV (ZREVRANGE).

2. Fair ties: put time inside the score

When two members have the same score, Redis orders them by member name. Stable, and unfair: on equal points, “zack” beats “amy” forever. The usual rule is that whoever got there first ranks higher, but a score is one number. So you build a composite score that sorts by points first and time second:

score = points × T + (T − 1 − reachedAt)  # T larger than any reachedAt
points = floor(score / T)                 # and back

More points always wins, because one point is worth T. On equal points, an earlier reachedAt gives a larger score. Two limits to respect: a score is a 64-bit float, exact for integers up to 253 (about 9 × 1015), so choose T and the maximum points so that points × T stays below it. And “reached at” means the time of the user’s latest counted solve, since deliveries can arrive out of order.

3. Correct under duplicates: one atomic script

Lesson 13 promised at-least-once delivery, so the same Accepted can arrive twice. The leaderboard must count each (user, problem) once. The check is a set: SADD lb:solved ada:p1 answers 1 the first time and 0 after. But “check, then add points” as two commands has a crash window: die between them, and the retry sees the solve recorded and skips the points, which are then lost for good.

Redis runs a Lua script atomically: nothing else executes in the middle (scripting with Lua). So the whole update is one EVAL:

if redis.call('SADD', KEYS[1], user .. ':' .. problem) == 0 then
  return 0
end
local points = redis.call('HINCRBY', KEYS[2], user, add)
-- …remember the latest time, compute the composite score…
redis.call('ZADD', KEYS[4], score, user)
return 1

One Lua trap: tostring(n) and the .. operator turn a number into a string with only 14 significant digits (on Redis 7.4, tostring(123456789012345) gives 1.2345678901234e+14). Numbers passed straight to redis.call keep their precision; when you need a number inside a string, use string.format('%.0f', n).

4. Derived data, and the order of writes

  • Postgres is the source of truth; Redis is a view. The solves live in Postgres. The board is derived data: computed from them, fast to read, and safe to lose, as long as you can rebuild it.
  • Write Redis after the commit. They don’t share a transaction. Before the commit, a rollback leaves points nobody earned. After it, the worst case is a missed update, which the idempotent retry or a rebuild repairs.
  • Rebuild aside, then swap. Build the new board under temporary keys, then RENAME them into place inside MULTI/EXEC, so readers never see a half-built board.

NestJS builds your objects for you: you write a constructor, and the service arrives with everything it needs. Today you build the machine that does that, in about 40 lines, so @Injectable, providers, @Inject(CODE_RUNNER) and “Nest can’t resolve dependencies” stop being magic words.

Why this matters

Tomorrow you write a whole new module: POST /submissions, a repository, a queue port. Every piece of it is wired by dependency injection. And “why does the worker inject a Symbol?” is an interview question you can now answer from first principles.

1. Who builds the objects?

Without DI, JudgeService would write new DockerRunner(new Config()) itself. Then it’s welded to Docker: its tests need Docker, and swapping the runner means editing it. With dependency injection, it just asks for “a code runner” in its constructor, and something else, the container, decides which one and builds it (Nest: providers).

The container needs three things for each dependency: a token (its name), a provider (how to build it: a class, a value or a factory) and a scope (how long it lives). Resolving a token is a depth-first walk of the dependency graph: build the dependencies first, then the consumer, remembering singletons. That walk is also where cycles show up, exactly like cycle detection in a graph DFS.

2. Tokens: why a Symbol

A class can name itself: JudgeService is both the type and the token. But the worker depends on the CodeRunner interface, and TypeScript erases interfaces when it compiles: at runtime, there’s nothing called CodeRunner to look up. So the port gets a runtime name, CODE_RUNNER = Symbol("CodeRunner"), and the constructor says @Inject(CODE_RUNNER). The module binds it: { provide: CODE_RUNNER, useClass: FakeCodeRunner } (custom providers).

How does Nest know a class’s dependencies without a deps list? With emitDecoratorMetadata, TypeScript writes the constructor’s parameter types into metadata that reflect-metadata reads at runtime. That’s why the worker imports reflect-metadata first. Your lab lists deps by hand instead: same idea, nothing hidden.

3. Lifetimes and borders

  • Singleton (Nest’s default): one instance for the whole app. Never keep request data in its fields: every request shares them (injection scopes).
  • Transient: a new instance for each consumer that injects it. Request: one per HTTP request, and everything that depends on it becomes request-scoped too.
  • Modules are borders: a provider is visible inside its module, and outside only if the module exports it (modules). That’s how the submissions module will use the queue without seeing BullMQ.

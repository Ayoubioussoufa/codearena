Why this matters

Iterator chains are how idiomatic Rust processes data, and they compile to the same loop you’d write by hand. You built CodeArena’s leaderboard on a Redis sorted set in lesson 18; today’s version computes the same kind of ranking from scratch, which is what you’d need for a contest’s final standings, a replay, or a frozen scoreboard.

1. Closures

A closure is an anonymous function that can capture variables from where it’s written: |s| s.minute > late reads late from the surrounding scope (The Book, §13.1). How it captures decides which trait it implements:

The closure…ImplementsCan be called
only reads its captures (or captures nothing)Fnany number of times, even from several places
changes a capture (count += 1)FnMutmany times, through a &mut
moves a capture out (returns it, drops it)FnOnceonce

A function that takes a closure says which it needs: fn count_where<F: Fn(&Submission) -> bool>(…, pred: F). The keyword move makes a closure take ownership of what it captures (essential for threads, lesson 38), but a move closure that only reads is still Fn.

2. Iterators: lazy adaptors, one consumer

An iterator is anything with a next() method. Adaptors (map, filter, enumerate, take_while, rev…) wrap an iterator in another and do nothing yet. A consumer (sum, count, max, position, collect, a for loop) pulls values through the whole chain, one at a time (§13.2).

let late_accepted: u32 = subs.iter()
    .filter(|s| s.accepted)          // nothing happens here…
    .map(|s| s.minute)               // …or here…
    .filter(|&m| m > 60)
    .count() as u32;                 // …until count pulls

No intermediate Vec is ever built, and the optimizer compiles the chain into one tight loop: in The Book’s benchmark the two versions ran within 2% of each other (§13.4). collect() builds whatever you ask for: a Vec, a HashMap, a String, even an Option<Vec<T>>, as in lesson 34.

3. HashMap, BTreeMap, and the entry API

map.entry(key) looks the key up once and lets you insert or update in place:

*counts.entry(team).or_insert(0) += 1;                   // count per team
teams.entry(team).or_default().entry(problem).or_default();  // nested maps

HashMap’s iteration order is unspecified, and its hasher is seeded randomly, so the order changes between runs (std docs). When order matters, sort explicitly, or use a BTreeMap, which keeps keys sorted. Sorting by several keys reads like a sentence: rows.sort_by(|a, b| b.solved.cmp(&a.solved).then(a.penalty.cmp(&b.penalty))).

4. Build the standings

ICPC scoring, as the regional rulebooks state it (ECNA rules): rank by problems solved, then by penalty minutes, lower first. A solved problem costs the minute of its first accepted run plus 20 per rejected run before it; rejected runs on unsolved problems cost nothing. src/lib.start.rs asks for standings, first_solvers, acceptance_rate, count_where and top.

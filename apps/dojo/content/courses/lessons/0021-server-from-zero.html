Why this matters

This afternoon you create CodeArena’s real server. Your sandbox lessons assumed the host is the last wall; if it falls, the attacker owns everything on it. That’s why the plan is “one small VM running Docker Compose and nothing else”, locked down before anything is deployed.

1. Keys, not passwords

With public-key authentication, you hold a private key that never leaves your machine, and the server holds the matching public key in ~/.ssh/authorized_keys. To log in, your client signs a challenge with the private key; the server checks the signature with the public key. Nothing guessable crosses the network, and a stolen authorized_keys file is useless to a thief.

# a modern, short key: ~/.ssh/id_ed25519(.pub)
ssh-keygen -t ed25519 -C "you@laptop"
# or paste the .pub line into authorized_keys
ssh-copy-id deploy@203.0.113.7

sshd is picky about that file, on purpose: with StrictModes (the default), it refuses keys in files or folders that other users could write (sshd_config). The convention is 700 for ~/.ssh and 600 for authorized_keys, owned by the user.

2. sshd’s defaults, and the five lines that fix them

OpenSSH’s defaults favour getting in over keeping out. Two surprise most people: PermitRootLogin defaults to prohibit-password, so root can log in with a key, and MaxAuthTries is 6. Put your settings in a drop-in file, /etc/ssh/sshd_config.d/50-hardening.conf, which the main config includes, so package upgrades don’t overwrite them:

PasswordAuthentication no
# the other way to ask for a password
KbdInteractiveAuthentication no
PermitRootLogin no
# everyone else is refused, whatever keys they hold
AllowUsers deploy
MaxAuthTries 3
X11Forwarding no

Never lock yourself out. Run sshd -t before restarting (a typo can stop sshd from starting, and you’re connected through it). Keep your current session open, and prove the new login works from a second terminal before closing it.

3. One user, least privilege

Create a deploy user, put it in the admin group (sudo on Ubuntu, wheel on Alpine), and log in only as that user. Day to day you don’t need root, so you shouldn’t have it by default; when you do, sudo asks and logs what ran. That’s least privilege, the same principle as dropping capabilities in lesson 7.

Alpine’s adduser -D creates a locked account (password field !), and OpenSSH refuses every login to a locked account, keys included: “User deploy not allowed because account is locked”. usermod -p '*' deploy sets a password field no password can match, without locking. The lab will show you this message if you forget.

4. A default-deny firewall, and the hole Docker makes in it

ufw default deny incoming
ufw default allow outgoing
ufw limit 22/tcp  # deny an address after 6 new connections in 30 s
ufw allow 80/tcp
ufw allow 443/tcp
ufw enable        # after allowing 22, or you cut your own connection

limit blunts brute-force scripts (ufw(8)). Then the trap that catches almost everyone: ports published by Docker bypass ufw. Docker routes them in the nat table, before the chains ufw filters, and its own documentation calls the two incompatible (Docker and ufw). A Compose file with 5432:5432 exposes Postgres to the internet, firewall or not. Lesson 22 closes that hole.

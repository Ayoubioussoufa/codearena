C reports failure with -1 and errno, which you can forget to check. TypeScript throws, which nothing in a function’s type tells you about. Rust puts the failure in the return type: a function that can fail returns a Result, and the caller has to decide what to do with the error. Today you parse a problem’s limits file into types, with every failure a value that names its line and its reason, and no unwrap anywhere.

Why this matters

A judge reads files written by people: problem configs, test cases, submissions. Each of those inputs will be wrong one day. The difference between “line 2: memory_mb is not a number: "256MB"” and a crash with a stack trace is the difference between a problem setter fixing it in ten seconds and opening an issue.

1. Result, and panics for bugs

Result<T, E> is an ordinary enum, Ok(T) or Err(E), so everything from lesson 31 applies: you match it, and the compiler won’t let you use the value without handling the error (The Book, §9.2).

Rust splits failures in two. Recoverable ones (a missing file, bad input, a refused connection) are Results. Bugs (an index past the end, a broken invariant) panic: the thread stops with a message. unwrap() converts the first kind into the second, which is right in tests and wrong for anything a user can cause (§9.3).

2. ?, the early return

fn load(path: &Path) -> Result<Limits, LoadError> {
    let text = std::fs::read_to_string(path)?;   // Err(io::Error)?  return it
    Ok(parse(&text)?)                            // Err(ConfigError)? return it
}

On Ok(v), expr? is v. On Err(e), it returns Err(From::from(e)) from the function. That From is how one function can return two kinds of error: LoadError has a variant for each, and a From impl per variant lets ? convert them. ? also works on Option, in functions returning Option.

Three tools keep the code flat: ok_or(err) turns an Option into a Result; map_err(|e| …) changes the error, for instance to add the line number; split_once('=') returns Option<(&str, &str)>. The |e| … is a closure, an inline function; lesson 35 covers them properly.

3. Errors people can read: Display

{:?} prints the Debug form for developers; {} prints the Display form, for users. You write Display yourself: an impl fmt::Display for ConfigError with one fmt method that matches on the variant and calls write!(f, "…"). That’s your first trait implementation; lesson 33 explains traits. Implementing std::error::Error too makes the type usable anywhere Rust expects an error, such as Box<dyn Error>.

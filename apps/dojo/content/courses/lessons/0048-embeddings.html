“My program is too slow on big inputs” and “time limit exceeded” share no words, yet they mean the same thing. Keyword search can’t see that. Embeddings can: they turn text into points in space, where meaning is a direction. Today you write the maths by hand and run an exact search over 10,000 vectors, then meet the index that makes it fast.

Why this matters

Friday’s build stores your notes as embeddings in Postgres with pgvector. Before you let an index do it for you, do it yourself once: then “cosine distance”, “dimensions” and “HNSW” stop being words in a config file.

1. What an embedding is

An embedding is a list of numbers, a vector, produced by an embedding model from a piece of text. The model is trained so that related meanings land close together (Vicki Boykis: What are embeddings). The vector dimension (how many numbers) is fixed by the model, often a few hundred to about a thousand. Jay Alammar’s illustrated word2vec shows the idea with pictures, from single words up (The illustrated word2vec).

Ollama serves embedding models too: POST /api/embed with { "model", "input" }, where input is a string or an array, and the answer is embeddings, one vector per input (Ollama: /api/embed).

2. Measuring “close”

a · b        = Σ a[i] × b[i]                 # dot product
|a|          = √(a · a)                      # length (norm)
cosine(a, b) = a · b / (|a| × |b|)           # −1 … 1: the angle only
L2(a, b)     = √Σ (a[i] − b[i])²             # straight-line distance
  • Cosine similarity compares directions and ignores length: [1, 1] and [10, 10] are identical to it. For text, direction is the meaning, so cosine is the usual choice.
  • On normalised vectors (length 1), the dot product is the cosine. That’s why many stores normalise once and use the cheaper inner product.
  • pgvector’s operators: <-> L2, <#> negative inner product, <=> cosine distance (1 − cosine), <+> L1 (pgvector).
  • Never mix models. Each embedding model invents its own space. Vectors from two models, even of the same length, can’t be compared.

3. Exact search, then approximate

Exact search compares the query with every vector and keeps the k best: perfect results, cost growing with the table. Like a sequential scan in lesson 15, it’s fine for thousands of rows and hopeless for millions.

Approximate nearest-neighbour (ANN) indexes visit only part of the data and accept missing a few true neighbours. pgvector offers two (pgvector):

  • HNSW, a layered graph of shortcuts (Malkov & Yashunin): better speed for the same recall than IVFFlat, slower to build, more memory;
  • IVFFlat: faster to build, less memory, slower queries.
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunk (id text PRIMARY KEY, text text, embedding vector(768));
CREATE INDEX ON chunk USING hnsw (embedding vector_cosine_ops);
SELECT id FROM chunk ORDER BY embedding <=> $1 LIMIT 4;

An index on a vector column supports up to 2,000 dimensions (halfvec: 4,000). Check your model’s dimension before you write the migration.

5. What this means for CodeArena

  • One embedding model, written down. Its name and dimension go in the env and the migration; changing it means re-embedding everything.
  • pgvector in the Postgres you already run: the image becomes pgvector/pgvector:pg16 (locally, in CI, in production), the column is Unsupported("vector(…)") in Prisma, the search a raw query.
  • Your notes are small (hundreds of chunks), so exact search would do. Add the HNSW index anyway, and say why in the interview: it’s the one you’d need at a million.

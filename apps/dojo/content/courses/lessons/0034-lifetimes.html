Today it stops inferring: a function with two inputs, a struct that holds a reference, a method whose result should outlive its borrow. You’ll write lifetime annotations, read them as promises, and build what every Rust competitive programmer keeps in a template: an input scanner whose tokens point into the input. A million characters, zero allocations, proven by a test.

Why this matters

Lifetimes are the part of Rust people call hard, and they’re the part that makes zero-copy parsing safe. Tokenizers, JSON parsers and HTTP servers in Rust hand out slices of their input instead of copies, and the compiler proves none of those slices outlives the buffer. You’ll use exactly this pattern in lesson 40’s tokenizer.

1. When the compiler asks

fn longest(a: &str, b: &str) -> &str {          // E0106: missing lifetime specifier
    if a.len() >= b.len() { a } else { b }
}

The result borrows from a or b, depending on the data, and the signature doesn’t say which. The caller needs to know, to check it doesn’t use the result after either input is gone. So you name the relationship (The Book, §10.3):

fn longest<'a>(a: &'a str, b: &'a str) -> &'a str

Read it as: for some region 'a where both inputs are valid, the result is valid too. In practice, the result lives as long as the shorter-lived input. Annotations don’t make anything live longer. They describe, and the compiler checks every caller against the description. At runtime they don’t exist.

2. Elision: the three rules that let you skip them

Most signatures need no annotations because the compiler applies three rules (§10.3, Lifetime Elision):

  1. Each reference parameter gets its own lifetime.
  2. If there’s exactly one input lifetime, every output reference gets it: fn first_word(s: &str) -> &str.
  3. In a method with &self or &mut self, outputs get self’s lifetime.

If the rules don’t settle every output, it’s E0106 and you write them. Rule 3 is the subtle one, and the lab plants a bug on it: a scanner method fn word(&mut self) -> Option<&str> compiles, but it promises the word borrows the scanner, so each word keeps the scanner mutably borrowed. The truth is that the word borrows the input, and the signature should say so.

3. Structs that borrow

pub struct Tokens<'a> {
    rest: &'a str,              // the part of the input not yet read
}
impl<'a> Iterator for Tokens<'a> {
    type Item = &'a str;        // each token borrows the input, not the iterator
    fn next(&mut self) -> Option<&'a str> { /* … */ }
}

A struct holding a reference carries a lifetime parameter, and no value of it may outlive what it borrows. Implementing Iterator means writing one method, next; you inherit count, map, collect and the rest, as lesson 33’s default methods promised. 'static is the lifetime of the whole program: string literals have it, because their bytes live in the binary.

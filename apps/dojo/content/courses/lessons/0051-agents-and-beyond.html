“Agent” is the most overloaded word in AI. Underneath, it’s a loop you can write in twenty lines: the model asks for a tool, your code decides whether to run it, the result goes back, repeat. Today you write that loop with the limits that keep it safe, then step back and map the levers beyond RAG, so you can say which one a problem needs.

Why this matters

The hint doesn’t need an agent, and knowing why is the senior answer. But interviews will ask about agents, tool use, MCP and fine-tuning. This lesson gives you each one in a sentence you can defend, and one you’ve built.

1. Tool use: the model asks, your code decides

With tool use, you describe some functions to the model (a name, a description, a JSON schema for the arguments). Instead of text, the model can answer with a request: “call get_failing_test with {"submissionId": "s42"}”. Your code runs it and sends the result back as a new message; the model continues. Ollama’s /api/chat accepts tools and returns tool_calls (Ollama API).

The model never runs anything itself. Every power a tool has, your code granted, which is why OWASP’s layers from lesson 45 live here: least privilege (read-only tools), and human approval for anything risky (OWASP LLM01).

2. Workflows and agents

Anthropic draws the line clearly (Building effective agents):

  • a workflow runs model calls through steps your code defines: prompt chaining, routing, an evaluator-optimizer loop;
  • an agent lets the model choose its own steps and tools, in a loop, until it decides it’s done.

Their advice is the whole lesson in one line: start with the simplest thing that works, and add agentic complexity only when it’s needed. CodeArena’s hint is a workflow: fetch the facts, retrieve, prompt, validate, store, the same steps every time. An agent earns its cost when the path can’t be written in advance, like debugging a repository you’ve never seen.

The Model Context Protocol (MCP) standardises the tool side: an open protocol for connecting AI applications to tools and data sources, so a tool written once works in any MCP client (MCP introduction).

3. The levers, in the order to pull them

  1. The prompt. Behaviour you can describe, fix here first, with the eval watching. Cheapest, fastest to change.
  2. Context: under about 200,000 tokens of knowledge, put it all in the prompt (Anthropic).
  3. Retrieval (RAG): knowledge that is large or changes often.
  4. Tools: facts that live in a system (a database, an API) and must be fresh.
  5. Fine-tuning: a consistent style or format that prompting can’t reach, with many good examples. LoRA freezes the original weights and trains small added matrices, so it fits on one GPU (Hu et al., 2021). Last, not first: it’s slow to iterate and easy to overfit.

Around all of them: evals (lessons 46–47) to know a change helped, guardrails (output validation, limits, approval) to bound the damage when it didn’t, and observability (log every prompt, output, token count and latency) to see what happened in production.

5. What this means for CodeArena

  • The hint stays a workflow. Its steps are known, so code runs them: predictable, testable, and cheap enough for a CPU.
  • If you ever add an agent (say, an admin assistant over submissions), it gets read-only tools, approval for any write, a step limit, and a log of every call.
  • The next lever is the prompt, then retrieval quality (lesson 50). Fine-tuning would be the answer only with thousands of graded hints and a style no prompt reaches.

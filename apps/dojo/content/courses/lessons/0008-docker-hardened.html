You’ve built every wall by hand: namespaces, cgroups, dropped capabilities, no_new_privs, a system-call filter, a deadline, an output cap. Docker can set all of them at once, with flags. Today you read every flag as the layer you already wrote, then build the runner CodeArena’s worker needs.

Why this matters

“Docker isn’t a sandbox by default” is true, and now you can say exactly why: by default a container keeps 14 capabilities, has a network, runs as root with no user namespace, and has no memory, process or CPU limit. Every flag below closes one of those, and you can name the kernel feature behind each. That’s the sentence that makes an interviewer lean forward.

1. What docker run actually does

docker run is a client (lesson 2). It asks the Docker daemon, which asks containerd, which runs runc, the component that does the real work. runc does what you did by hand: clone with namespace flags (lesson 5), cgroup files (lesson 6), capabilities, no_new_privs and a seccomp filter (lesson 7), mounts, then exec. Nothing magic happens anywhere: it’s your box, cage and guard, with more care.

Try it (2 minutes). The whole hardened run, then look at it from inside:

H="--rm --network none --read-only --tmpfs /tmp:rw,noexec,nosuid,size=16m \
   --memory 128m --memory-swap 128m --pids-limit 64 --cpus 1 \
   --cap-drop ALL --security-opt no-new-privileges --user 65534:65534"
docker run $H python:3.12-alpine sh -c '
  grep -E "CapEff|CapBnd|NoNewPrivs|Seccomp:" /proc/self/status
  cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/pids.max /sys/fs/cgroup/cpu.max
  id; ip -o link | wc -l; touch /x'

Every line is a lesson: capabilities and bounding set at zero (7), NoNewPrivs: 1 and Seccomp: 2 (7), the three cgroup files you wrote yourself (6), nobody (5 and 7), one interface (5), and “Read-only file system”.

3. Four decisions a runner makes

  1. How the code gets in. Never as an argument: arguments are visible to every user in ps, and the kernel caps their size (ARG_MAX). Write it to a fresh temporary folder and bind-mount that folder read-only (-v <dir>:/code:ro); the test’s input goes on stdin (lesson 3). Make the folder and file world-readable, because the program runs as nobody.
  2. Which image. Pinned to an exact tag, never latest: the same interpreter every run, and the limits you calibrated still mean something.
  3. A name per run. --name lab8-<random>, so you can find the container again, whatever happens to your client.
  4. Kill and clean up through the daemon. At the deadline, docker kill <name>. Afterwards, ask docker inspect -f '{{.State.OOMKilled}}' <name> (so no --rm: the container must still exist to be asked), then docker rm -f <name> and delete the folder, in a finally. That’s I-17, fixed.

A cost to know: starting a container takes a few hundred milliseconds (about 0.45 s in this lesson’s tests). Measured around docker run, every solution pays it. Either measure the program inside (its cgroup’s CPU time), or calibrate your limits with it included, and write down which.

4. Build docker-runner.mjs

The contract is in docker-runner.start.mjs: runInDocker({ source, input, timeoutMs, memoryMb, maxOutputBytes }) runs Python source in a fresh hardened python:3.12-alpine container named lab8-…, and resolves with { outcome, exitCode, stdout, stderr, timeMs }, where outcome is exit, timeout, output-limit, memory-limit or spawn-error. Afterwards, no container and no temporary folder may remain. It builds on your lesson 4 runner: you reuse it as is.

5. What this means for a judge

  • You can defend every flag, because you built what it does. “Docker isn’t a sandbox by default” becomes a list, not a slogan.
  • The runner reports facts. memory-limit, timeout, output-limit, an exit code: the verdict comes later, from the judge loop (lesson 9).
  • Every run must clean up after itself, or a busy judge fills the host with dead containers and temporary files. The checker’s last case is a production habit.
  • Stronger walls exist. gVisor intercepts system calls in a user-space kernel; Firecracker runs each submission in a micro-VM. At scale they’re the right answer, and saying why you don’t need them yet is ADR-007.

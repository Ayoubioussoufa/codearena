Ask a team how good their AI feature is, and most will show you a demo. Ask how they know, and the good ones show you a number from an eval that runs on every change. Today you build the core of yours: rules written in code, a score over several runs, and a gate that fails the build.

Why this matters

Evals are why you added the AI feature to the sprint: they’re what job descriptions mean by “AI engineering”. Without them, a prompt change is a guess. With them, “the hint got better” is a number in a PR.

1. Why evals, and what one is

An eval is a repeatable measurement of an AI feature’s output against criteria you wrote down first (Anthropic: develop tests). It has three parts:

  • a test set: inputs that look like real use, including the hard and the hostile ones;
  • graders: what decides pass or fail for each output;
  • a score, tracked over time, so a change that makes things worse is caught.

Hamel Husain’s point, from many shipped products: teams that succeed with AI features iterate on evals, not on vibes, and they read the outputs, not just the scores (Your AI product needs evals).

2. Graders, cheapest first

  1. Code-based graders wherever the question has an exact answer: valid JSON? at most three sentences? no line of the reference solution? names the failure? Fast, free, never wrong.
  2. A judge model for what code can’t decide, such as “would this help a beginner?”. Lesson 47 is about trusting one.
  3. A human (you) to label the first cases and calibrate both.

For the hint, the most important rule is a code rule: no line of the solution. Compare with whitespace removed, so re-indenting doesn’t hide a leak, and skip short lines like } or s = 0; that any hint may mention.

3. Rates, flaky cases, and the gate

  • Run each case several times. The output varies (lesson 43), so one run is an anecdote. Report the pass rate: passing runs over all runs.
  • Report per rule, not just overall: “noSolutionLeak 100%, maxSentences 70%” tells you what to fix.
  • List the flaky cases: the ones that pass sometimes. They’re where the prompt is on an edge.
  • Gate on a threshold in CI: below it, the job fails, exactly like a failing test. Run it only when the prompt, the model or the cases change: it’s slow.

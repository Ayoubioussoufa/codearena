Between “a request arrives” and “your controller runs”, NestJS passes it through five kinds of components, in a fixed order. Most bugs in a Nest API are a concern placed in the wrong one: validation that runs before authentication, an error message that leaks, a timer that misses half the work. Today you build the pipeline yourself, so the order stops being something to memorise.

Why this matters

Tomorrow’s POST /submissions touches every stage: the auth guard, the throttler, a validation pipe with a size cap, and the exception filter that I-3 says is dropping your messages. Knowing where each one runs is the difference between wiring them and debugging them.

1. Five stages, one order

NestJS documents its request lifecycle precisely (request lifecycle):

request → middleware → guards → interceptors (before) → pipes → handler
        ← interceptors (after) ← result
any error → exception filters → response
  • Middleware sees the raw request before Nest has even chosen a handler: plumbing like cookie-parser. It can answer on its own by never calling next().
  • Guards answer one question: may this request go on? false becomes 403 Forbidden resource; throwing UnauthorizedException gives a 401 (guards).
  • Interceptors wrap the handler on both sides: they can time it, cache it, or reshape its result (interceptors).
  • Pipes prepare the handler’s arguments: transform them, or validate and refuse with a 400 (pipes).
  • Exception filters turn any exception thrown after middleware into a response (exception filters).

Within guards, interceptors and pipes, the order is global, then controller, then route. Two exceptions to remember: interceptors unwind in reverse after the handler (each wraps the next, like an onion), and filters resolve from the route up (route first, global last, and a handled exception stops there).

2. Fail safely

Every pipeline has a last line: an exception nobody handled. It must become a response that tells the client nothing about your internals. An HttpException (or your lab’s HttpError) was thrown on purpose, so its status and message are meant for the client. Anything else, a Prisma error or a bug, is a 500 Internal server error, with its real message kept for your logs. An error text like connect ECONNREFUSED db.internal:5432 in a response is a security bug, as OWASP’s guidance on error handling explains (Error Handling Cheat Sheet).

That’s also where I-3 lives. The ValidationPipe puts its messages in the exception’s response, and a filter that only reads exception.message replaces them with “Bad Request Exception”.

4. What this means for CodeArena

  • Authentication is a global guard, with @Public() as the way out: you already have it. Rate limiting is the throttler guard, which belongs on POST /submissions: judging is the most expensive thing you do.
  • Validation is a pipe with a DTO: code as a string with a maximum size, the language from your enum, the problem id.
  • The all-exceptions filter must pass validation messages through (I-3) and never leak anything else.

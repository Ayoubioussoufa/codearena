“A 7B model, quantized to 4 bits” sounds like jargon. It’s arithmetic, and it decides whether the hint runs on your laptop, on your VM, or nowhere. Today you learn to do that arithmetic, then write the client that talks to your own model: one that never trusts what comes back.

Why this matters

You chose to host the model yourself instead of calling a paid API. That choice comes with three jobs: picking a model that fits the hardware, serving it, and handling its mistakes. This lesson covers all three, and the client you build is the adapter behind CodeArena’s HintGenerator port.

1. Open weights, and what “7B” means

An open-weights model is one whose trained numbers you can download and run yourself. Those numbers are its parameters: “7B” means about 7 billion of them. Every one is read for every token generated, so they must sit in memory, ideally the GPU’s.

How much memory is a question of precision. Quantization stores each parameter with fewer bits, trading a little quality for a lot of space (Hugging Face: quantization):

weights memory ≈ parameters × bytes per parameter
7B at 16 bits  ≈ 7 × 2   = 14 GB
7B at 8 bits   ≈ 7 × 1   =  7 GB
7B at 4 bits   ≈ 7 × 0.5 = 3.5 GB      # fits a 12 GB GPU with room to spare

Then add headroom. The context needs memory too (the KV cache, which grows with the context length you allow, Ollama’s num_ctx option), and so does the runtime. A rule of thumb: plan for the weights plus a few GB.

2. Ollama: a model behind an HTTP API

Ollama downloads models, loads them on the GPU (or the CPU), and serves them over HTTP on port 11434. The call you’ll use is POST /api/chat (Ollama API):

{ "model": "<a model you pulled>",
  "messages": [{ "role": "system", "content": "…" },
               { "role": "user",   "content": "…" }],
  "stream": false,                 # default true: chunks as they come
  "options": { "temperature": 0 },
  "format": { …a JSON schema… } }

The answer carries message.content and counters: prompt_eval_count (tokens read), eval_count (tokens written), and durations in nanoseconds: total_duration, load_duration, prompt_eval_duration, eval_duration. Tokens per second is eval_count / eval_duration, with the duration converted to seconds.

3. JSON you can trust

format accepts "json" or a JSON schema, and Ollama constrains the output to it (Ollama: structured outputs). Treat that as help, not a guarantee. Your code is the contract the rest of CodeArena relies on, so the client follows lesson 14’s instinct for anything outside your control:

  • Parse and check every reply against the schema’s required fields.
  • Retry once on a bad reply: generation is random enough that a second try often succeeds.
  • Then fail cleanly, with an error that says “invalid output”, so the job records a failure instead of showing garbage.
  • Never retry an HTTP error. A 404 (model not pulled) or a 500 (out of memory) won’t fix itself in a millisecond: let the queue’s backoff handle it.

5. What this means for CodeArena

  • Two sizes, one setting. On your laptop’s GPU, a 7B model at 4 bits answers in a few seconds. On a VM’s CPU, a 3B one is the realistic choice. HINT_MODEL in the env makes that a config change, not a code change.
  • The hint is a job, not a request. Tens of seconds on a CPU is too long to hold an HTTP request open: POST /submissions/:id/hint answers 202 and enqueues; the worker calls the model.
  • This client is the adapter. Behind a HintGenerator port, with a fake for unit tests, exactly like the code runner and the queue.

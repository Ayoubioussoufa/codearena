In C, every malloc needs exactly one free, and nothing checks it: free too early and you read garbage, twice and you corrupt the heap, never and you leak. Rust answers with one idea, ownership: every value has one owner, and the owner’s scope decides when it’s freed. Today you learn to say who owns what at every line, then you fix five functions that break the rules, without cheating.

Why this matters

Ownership is the idea the rest of Rust builds on. Borrowing (lesson 30), lifetimes (34) and thread safety (38) all follow from it. It’s also the answer to “why is Rust memory-safe without a garbage collector?”, an interview question with a precise answer you’ll be able to give after today.

1. Three rules

The Book states them in three lines (§4.1):

  1. Each value has an owner, a variable.
  2. There is only one owner at a time.
  3. When the owner goes out of scope, the value is dropped.
{
    let s = String::from("judge");   // s owns a heap buffer holding "judge"
    // ... use s ...
}                                    // s goes out of scope: the buffer is freed, here

The compiler inserts the free at the closing brace, the way you’d write free(s) before returning in C, except it can’t be forgotten and can’t happen twice. Rule 2 is what makes “twice” impossible.

2. Stack, heap, and what a String is

A String is three numbers on the stack (a pointer, a length, a capacity) and the bytes on the heap, exactly the struct you’d write in C for a growable buffer:

stack: s = { ptr ──────┐, len: 5, cap: 5 }
                       ▼
heap:                [ j u d g e ]

Now ask what let t = s; should do. Copying the three numbers gives two structs pointing at one buffer, and at the end of the scope both would free it: C’s double free. Copying the buffer too would be a hidden allocation on every assignment. Rust does neither.

3. Move, Copy, clone

  • Move. let t = s; copies the three numbers and makes s unusable. One owner, one free. Using s afterwards is error E0382, “borrow of moved value”. Passing s to a function that takes a String moves it too, and so does v.push(s).
  • Copy. Types that live entirely on the stack, with nothing to free (integers, bool, char, shared references, tuples of these), are copied instead. That’s why let b = a; leaves an i32 a usable.
  • clone. s.clone() allocates a second buffer and copies the bytes: two independent owners. It’s always explicit, so you can see every copy in the code.

Functions follow the same rules. A parameter of type String takes ownership, and the value is dropped when the function ends unless it’s returned. A parameter of type &str or &String only borrows: the function reads it, and the caller still owns it afterwards. Lesson 30 is all about borrows; today you only need the &.

4. The compiler suggests .clone(). Don’t.

When you move something you still need, rustc often offers two fixes: borrow (&argv[0]) or clone (argv[0].clone()). Both compile. The clone copies data so you never have to decide who owns it, and code written that way is slow and hides its design. Experienced Rust programmers read “borrow of moved value” as a question: does this code need its own copy, or does it only need to look? It almost always only needs to look.

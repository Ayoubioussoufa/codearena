A judge doesn’t just run a program. It hands it a test’s input and keeps what it prints, to compare with the expected answer: that’s the stdin/stdout judging from ADR-006. Today run learns to do it, and you meet the two traps every judge falls into once: output that never stops, and a wiring mistake that freezes a correct program until the deadline calls it too slow.

Why this matters

Both traps are invisible in testing and show up in production. Small outputs fit in the kernel’s buffers, so the deadlock never happens on your laptop’s examples. Then someone submits a solution that prints 300 KB, it’s correct, and your judge says Time Limit Exceeded. Today you learn why, and build the design real judges use to make it impossible.

1. File descriptors

When a process opens a file, the kernel gives it back a small integer: a file descriptor, an index into that process’s table of open files. By convention, three are already open when a program starts: 0 is stdin, 1 is stdout, 2 is stderr.

Here’s the key: read(0, …) means “read from whatever fd 0 points to”. That could be a terminal, a file, or a pipe. The program doesn’t know which, and doesn’t care. And the table is inherited: a child gets a copy of its parent’s descriptors at fork, and keeps them through exec. That’s why echo hi printed straight into your lesson 1 checker.

Try it (2 minutes). Watch fd 0 change:

ls -l /proc/self/fd
ls -l /proc/self/fd < /etc/hostname
echo hi | ls -l /proc/self/fd

First, 0 points to your terminal (/dev/pts/…). Then to /etc/hostname. Then to pipe:[…]. Same program, three different stdins, chosen by the shell before ls even started. (The extra fd 3 is the directory ls opened to list it.)

2. Redirection happens in the gap

You did this in minishell. To make a child’s stdin a file, do it in the child, between fork and exec:

  1. open the file, which gives you some fd, say 3;
  2. dup2(3, 0) makes fd 0 point to the same open file as fd 3 (closing whatever 0 pointed to before);
  3. close(3), because the program doesn’t need two handles on the same file;
  4. exec: the new program reads “its stdin” and gets the file.

The same three moves on fd 1 send stdout to a file. That’s all < and > ever were.

/dev/null is a file that’s always empty to read (end of file right away) and swallows anything written to it.

Two rules for a judge. First, never let a submission inherit your stdin. If the worker was started from a terminal, a program calling input() would sit waiting for a keyboard until the deadline. With no test input, give it /dev/null. Second, open the files in the parent, before fork, so a bad path becomes a clear error from your runner instead of a mysterious exit 127 from the child.

3. Pipes, and the deadlock

A pipe is a buffer inside the kernel with two file descriptors: one end to write into, one to read from. When you type a | b, the shell creates a pipe, points a’s stdout at the write end and b’s stdin at the read end, and both run at the same time.

Three rules (from pipe(7)) explain everything that can go wrong:

  • Reading an empty pipe blocks while any write end is open, anywhere. It returns 0 (end of file) only once every write end is closed, including copies inherited by children.
  • Writing to a full pipe blocks until the reader makes room. On Linux, a pipe holds 65,536 bytes by default.
  • Writing with no reader left sends the writer SIGPIPE.

Try it (3 minutes). First, measure the buffer:

python3 - <<'EOF'
import os
r, w = os.pipe()
os.set_blocking(w, False)
n = 0
try:
    while True:
        n += os.write(w, b"x" * 1024)
except BlockingIOError:
    print(n, "bytes fit in the pipe before a write would block")
EOF

Then watch a writer get stuck. The reader waits 3 seconds before reading:

python3 -c "import sys; sys.stdout.write('x' * 1000); sys.stderr.write('done writing\n')" | (sleep 3; wc -c)
python3 -c "import sys; sys.stdout.write('x' * 100000); sys.stderr.write('done writing\n')" | (sleep 3; wc -c)

With 1,000 bytes, “done writing” appears at once: everything fit in the pipe. With 100,000, it appears only after 3 seconds. The writer was frozen at the 65,537th byte until wc started reading.

The deadlock

Now picture the obvious way to capture a child’s output: point its stdout at a pipe, waitpid until it ends, then read the pipe. With a small output, that works. With 300 KB, the child fills the pipe and blocks in write, waiting for you to read. But you’re blocked in waitpid, waiting for it to end. Each waits for the other, forever, until the deadline kills a correct program and reports a TLE. Feeding a large input through a pipe before reading the output fails the same way.

This is a famous bug. Python’s documentation warns that Popen.wait() “will deadlock when using stdout=PIPE” and points to communicate(), which reads while it waits (subprocess docs).

There are two ways out. Either read while it runs (watch the pipe with poll() and empty it as data arrives, with the deadline as the timeout), or don’t use pipes: point stdin and stdout at files, which never fill up and never block. Real judges use files: the IOI’s isolate has --stdin and --stdout options that redirect them to files, and --fsize to cap what it writes (isolate’s manual). That’s what you build today. Reading while it runs is today’s challenge, and in lesson 4 Node does it for you, with its event loop.

4. Capping the output, with the kernel

Files fix the deadlock but open a new hole: yes prints “y” forever, and at hundreds of megabytes a second it would fill your disk before the deadline. You need a cap, and the kernel has one built in.

setrlimit(RLIMIT_FSIZE, …) sets the largest size any file may reach through this process. The kernel lets a file grow up to the limit, and the first write that tries to go past it gets SIGXFSZ (signal 25), whose default action kills the process. Like every resource limit, it’s inherited across fork and exec, so you set it in the gap and it binds the program and everything it starts.

Try it (2 minutes). The shell’s ulimit -f sets the same limit, in blocks of 1,024 bytes:

( ulimit -f 10; yes > /tmp/yes.txt ); echo "exit=$?"; ls -l /tmp/yes.txt
( ulimit -f 10; python3 -c "import sys; sys.stdout.write('x' * 20000)" > /tmp/py.txt ); echo "exit=$?"

yes dies with 153, which is 128 + 25: SIGXFSZ. Its file holds exactly 10,240 bytes. Python is different: it prints OSError: File too large and exits with 120.

Why Python didn’t die

Python ignores SIGXFSZ at startup, on purpose. When a program ignores it, the kernel refuses the write with the error EFBIG instead, and Python turns that into an exception. This one surfaces when Python flushes its buffer at shutdown, hence 120. So how the program died tells you nothing reliable. The limit held either way, and the file’s size is the fact to trust.

One last detail. With the limit set to exactly the cap, an honest program that prints exactly the cap and a flood that tries to print more both leave a file of the same size. So set the limit to cap + 1: an honest program never goes past the cap, and anything that tried to write more leaves cap + 1 bytes behind. Size greater than the cap means output-limit, whatever the exit status.

5. Build: run, with input and output

Usage: ./run -t <ms> [-i <input>] -o <output> [-m <max bytes>] <program> [args...]

  • The program’s stdin is the -i file, or /dev/null without -i.
  • Its stdout goes to the -o file. It may write at most -m bytes (default 8 MiB, 8,388,608).
  • The deadline and the process group work as in lesson 2.

Then run prints exactly three lines:

  • line 1: output-limit if the output file is bigger than -m, else timeout, else exit N or signal S;
  • line 2: time_ms=T;
  • line 3: output_bytes=B, the output file’s size.

A missing -t, -o or program, a bad number, or an input file that can’t be opened prints a usage line on stderr and exits with 2.

Why the + in "+t:i:o:m:"? By default, GNU getopt scans the whole command line, so in ./run -t 500 -o out sh -c 'exit 5' it would try to read -c as one of your options. + tells it to stop at the first word that isn’t an option: the program’s name.

Challenge: through a pipe, without the deadlock

Capture stdout through a pipe instead of pointing it at the file. Your runner reads the pipe and writes into the -o file itself, so the checker doesn’t change. First, build the naive version on purpose: waitpid, then read. Watch the 300 KB case freeze until the deadline: the deadlock, with your own hands.

Then fix it with poll(): wait on the read end with the time left as the timeout, read whatever is there, stop at cap + 1 bytes (kill the group: that’s your output-limit), and finish when read returns 0. Two traps: close the parent’s copy of the write end right after fork (or you never see end of file), and reap the child after the end of file.

6. What this means for a judge

  • Files are the safe default. Input and output through files can’t deadlock, the kernel enforces the cap, and nothing piles up in the judge’s memory.
  • Pipes need a reader that never stops. When you can’t use files (and CodeArena’s worker talks to docker run -i through pipes), you must read while the program runs, and cap it yourself. That’s lesson 4.
  • Trust facts, not stories. The file’s size is a fact. An exit code is the program’s own story, and lesson 1 already showed it can lie.
  • stderr needs the same care. A crash can print megabytes of stack trace, so it needs a cap too, and it must never be shown to another user.
